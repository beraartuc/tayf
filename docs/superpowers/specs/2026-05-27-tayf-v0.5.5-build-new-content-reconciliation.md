## §5 — PendingEdits → DocumentMut walk algoritması

### §5.1 — Top-level orchestrator (`apply_edits`)

```rust
pub(crate) fn apply_edits(
    doc: &DocumentMut,
    edits: &PendingEdits,
) -> Result<String, ReconcileError> {
    let mut doc = doc.clone(); // Defensive — snapshot.doc dokunulmaz
    apply_general(&mut doc, &edits.general)?;
    for (rule_id, rule_edit) in &edits.rules {
        match rule_id {
            RuleId::UserConfig(name) => apply_user_config_rule(&mut doc, name, rule_edit)?,
            // v0.5.4 tabs sadece UserConfig stage ediyor; defensive skip:
            RuleId::Builtin(_) | RuleId::Embedded { .. } | RuleId::DiskProfile { .. } => {
                // No-op: edit'ler bu variants altında staged değil; v0.6+ bu paths wire'lanır
            }
        }
    }
    for new_rule in &edits.added {
        apply_new_rule(&mut doc, new_rule)?;
    }
    for rule_id in &edits.deleted {
        apply_deletion(&mut doc, rule_id)?;
    }
    Ok(doc.to_string())
}
```

**Order of operations (deterministic for test pinning):**
1. General — `[general]` table mutations en başta (doc'un en altında ya da en üstündeki [general]'ı bulur, mevcut konum korunur).
2. UserConfig rule edits — HashMap iter order non-deterministic, ama her edit ATOMİK ve birbirinden bağımsız (rule_id unique). Test'lerde tek-edit case'leri kullanılır; multi-edit test'lerde HashMap iter order'ı assertion'ı bozmaz çünkü output'un her satırını ayrı pin'leriz.
3. New rules append — sondan başlar; Vec order korunur.
4. Deletions — son; en güvenli (önce edit, sonra silme — referential consistency için).

### §5.2 — `apply_general(doc, &GeneralEdits)`

```rust
fn apply_general(doc: &mut DocumentMut, ge: &GeneralEdits) -> Result<(), ReconcileError> {
    if ge.is_empty() { return Ok(()); }
    let general = ensure_general_table(doc);
    match &ge.theme {
        None => {} // unedited — preserve disk state
        Some(None) => { general.remove("theme"); }
        Some(Some(name)) => { general["theme"] = toml_edit::value(name.as_str()); }
    }
    match &ge.profile {
        None => {}
        Some(None) => { general.remove("profile"); }
        Some(Some(name)) => { general["profile"] = toml_edit::value(name.as_str()); }
    }
    Ok(())
}

fn ensure_general_table(doc: &mut DocumentMut) -> &mut toml_edit::Table {
    if !doc.contains_key("general") {
        let mut t = toml_edit::Table::new();
        t.set_implicit(false); // Açık `[general]` header — implicit-dotted değil
        doc["general"] = toml_edit::Item::Table(t);
    }
    doc["general"].as_table_mut().expect("ensured above")
}
```

**Tri-state pin'leri:**
- `None` — disk state preserve (key var ise korunur; yok ise yok kalır).
- `Some(None)` — key DELETE (TUI'de user explicit clear etti).
- `Some(Some(s))` — key SET (TUI'de user yeni name seçti).

### §5.3 — `apply_user_config_rule(doc, name, &RuleEdit)`

```rust
fn apply_user_config_rule(
    doc: &mut DocumentMut,
    name: &str,
    edit: &RuleEdit,
) -> Result<(), ReconcileError> {
    let rules = ensure_rules_array(doc);
    let idx = find_rule_index_by_name(rules, name);
    let rule_table = match idx {
        Some(i) => rules.get_mut(i).expect("idx valid").as_table_mut().ok_or_else(|| {
            ReconcileError::TypeMismatch {
                path: format!("rules[{i}]"),
                expected: "table",
                actual: rules.get(i).map_or("missing", |v| v.type_name()),
            }
        })?,
        None => {
            let mut t = toml_edit::Table::new();
            t["name"] = toml_edit::value(name);
            rules.push(t);
            rules.get_mut(rules.len() - 1).expect("just pushed").as_table_mut().expect("just made")
        }
    };
    if let Some(pat) = &edit.pattern {
        rule_table["pattern"] = toml_edit::value(pat.as_str());
    }
    for (style_key, ns) in &edit.styles {
        let style_table = match style_key {
            StyleKey::Default => {
                ensure_inline_or_table(rule_table, "style")?
            }
            StyleKey::Numbered(i) => {
                let styles = ensure_subtable(rule_table, "styles")?;
                ensure_inline_or_table(styles, &i.to_string())?
            }
            StyleKey::Named(n) => {
                let styles = ensure_subtable(rule_table, "styles")?;
                ensure_inline_or_table(styles, n.as_str())?
            }
        };
        write_style_table(style_table, ns)?;
    }
    Ok(())
}
```

**ensure_rules_array:** `doc.entry("rules").or_insert(ArrayOfTables::new())` benzeri; type mismatch ise `ReconcileError::TypeMismatch`.

**find_rule_index_by_name:** linear scan, ilk eşleşen `name = "X"` index'i.

**ensure_inline_or_table:** mevcut anahtar varsa inline-table (or table) olarak `&mut Table` dön; yoksa yeni boş inline-table oluştur. toml_edit API'sinde `style = { fg = "red" }` ile `[rules.style]` arasındaki ayrım `Item::Value(Value::InlineTable(...))` vs `Item::Table(...)`. Spec phase'de exact toml_edit ergonomics'ini doğrularız (e.g., `as_inline_table_mut` + `as_table_mut` her ikisini de handle).

### §5.4 — `write_style_table(table, &NewStyle)`

```rust
fn write_style_table(
    table: &mut /* InlineTable or Table */,
    ns: &NewStyle,
) -> Result<(), ReconcileError> {
    match &ns.fg {
        None => {}
        Some(None) => { table.remove("fg"); }
        Some(Some(color)) => { table["fg"] = value(color.to_toml_str()); }
    }
    match &ns.bg {
        None => {}
        Some(None) => { table.remove("bg"); }
        Some(Some(color)) => { table["bg"] = value(color.to_toml_str()); }
    }
    if let Some(b) = ns.bold { table["bold"] = value(b); }
    if let Some(b) = ns.italic { table["italic"] = value(b); }
    if let Some(b) = ns.underline { table["underline"] = value(b); }
    if let Some(b) = ns.dim { table["dim"] = value(b); }
    Ok(())
}
```

**InlineTable vs Table** — spec phase'de tek bir helper kanonikleştirilir; toml_edit API'sinde `&mut Item` üzerinden `as_value_mut().and_then(|v| v.as_inline_table_mut())` ya da `as_table_mut()` chain'i kullanılır. Yardımcı `enum StyleTarget<'a> { Inline(&'a mut InlineTable), Table(&'a mut Table) }` ile dispatch eder.

**Bool tri-state notu:** v0.5.4 `NewStyle.bold: Option<bool>` — `None` = skip, `Some(true/false)` = set. **Disk-side bool clear yok** — kullanıcı `bold = false` derse hem "set to false" hem "remove bold key" anlamına gelebilir; v0.5.5 contract: set-to-bool-value (clear yok). Disk'te `bold = false` satırı kalır (functionally `bold = false` ile `bold` absent same). v0.6+ ColorPicker UI bu nüansı revisit edebilir.

### §5.5 — `apply_new_rule(doc, &NewRule)`

```rust
fn apply_new_rule(doc: &mut DocumentMut, rule: &NewRule) -> Result<(), ReconcileError> {
    let rules = ensure_rules_array(doc);
    let mut t = toml_edit::Table::new();
    t["name"] = value(rule.name.as_str());
    t["pattern"] = value(rule.pattern.as_str());
    let mut style_inline = toml_edit::InlineTable::new();
    // Inline yazımı tercih edildi — v0.5.5'te yeni rules style = { ... } shape'ine yazılır
    // (mevcut user-config dosyaları çoğunlukla inline-style kullanır).
    write_style_inline(&mut style_inline, &rule.style)?;

        t["style"] = Item::Value(Value::InlineTable(style_inline));
    }
    rules.push(t);
    Ok(())
}
```

**Inline tercih rationale:** Mevcut user-config dosyaları + assets/profiles/*.toml hep inline (e.g., `style = { fg = "cyan" }`). v0.5.5 yeni rules için aynı stil benimsenir; spec §10.4'te user-facing format documentation güncellenir (gerekmez — README zaten inline gösteriyor).

### §5.6 — `apply_deletion(doc, &RuleId)`

```rust
fn apply_deletion(doc: &mut DocumentMut, rule_id: &RuleId) -> Result<(), ReconcileError> {
    match rule_id {
        RuleId::UserConfig(name) => {
            let rules = doc.get_mut("rules")
                .and_then(|it| it.as_array_of_tables_mut());

                if let Some(idx) = find_rule_index_by_name(arr, name) {

                }
            }

        }
        RuleId::Builtin(_) | RuleId::Embedded { .. } | RuleId::DiskProfile { .. } => {
            Err(ReconcileError::UnsupportedDeletionTarget {
                rule_id: format!("{rule_id:?}"),
            })
        }
    }
}
```

```rust
impl Color {
    /// Encode self as a canonical TOML configuration string. Roundtrip
    /// property with `Color::parse_str` is pinned by test.
    pub(crate) fn to_toml_str(self) -> String {
        match self {
            Color::Black => "black".into(),
            Color::Red => "red".into(),
            Color::Green => "green".into(),
            Color::Yellow => "yellow".into(),
            Color::Blue => "blue".into(),
            Color::Magenta => "magenta".into(),
            Color::Cyan => "cyan".into(),
            Color::White => "white".into(),
            Color::BrightBlack => "bright_black".into(),
            Color::BrightRed => "bright_red".into(),
            Color::BrightGreen => "bright_green".into(),
            Color::BrightYellow => "bright_yellow".into(),
            Color::BrightBlue => "bright_blue".into(),
            Color::BrightMagenta => "bright_magenta".into(),
            Color::BrightCyan => "bright_cyan".into(),
            Color::BrightWhite => "bright_white".into(),
            Color::Indexed(n) => format!("color({n})"),
            Color::Rgb(r, g, b) => format!("#{r:02x}{g:02x}{b:02x}"),
        }
    }
}
```

**Canonical form choices:**
- ANSI names: lowercase (parse_str case-insensitive ama canonical lowercase ile başlamak yeni-yazılan dosyada tutarlı görünüm sağlar).
- Indexed: `"color(n)"` — parse_str'in 256-palette form'u.
- Rgb: `#rrggbb` — parse_str'in hex form'u; lowercase + zero-pad. `"rgb(r,g,b)"` form'u da parse'lanır ama yazımda hex daha kompakt ve roundtrip-stable.

## §10 — Açık sorular (paralel spec review surface)

1. **toml_edit `InlineTable` vs `Table` dispatch ergonomics** — v0.5.5'te `write_style_table` her iki form'u da handle eder mi yoksa tek bir canonical form'a zorlar mı? Spec §5.4 enum `StyleTarget` proposal. Rust senior spec review verdict.
2. **Hash impl on `RuleId`** — `Debug` impl `{:?}` ile rule_id Display'lenir; bu format `{:?}` çıktısı stabil mi yoksa test'leri kıracak şekilde değişir mi? Memory `feedback_test_assertion_specificity`. ReconcileError::UnsupportedDeletionTarget Display'i `Debug` format kullanırsa test #14 byte-pin'i hassas olur. Alternative: `format!("{}", rule_id_as_user_string)` benzeri custom encoding (Builtin("uuid") → `"builtin:uuid"`, Embedded { profile, rule } → `"embedded:{profile}:{rule}"`, vb.). Spec phase decision.
3. **`commit_save` Result<String, ReconcileError> error message wrapping** — `format!("reconcile failed: {e}")` vs `format!("save failed: reconcile error: {e}")`. Düz tek-prefix tercih ediliyor; spec phase test pin'i ile tutarlılaştırılır.
4. **`apply_deletion` ordering** — apply_edits içinde deletions en sonda; ama eğer user önce override staged (rules HashMap) sonra delete staged (deleted set) ise iki aynı RuleId aynı PendingEdits'te bulunabilir mi? `is_dirty()` her ikisini de dirty saysa da, reconcile semantik'i: delete latest stage. v0.5.5 contract: deletions rules'tan sonra çalışır, yani staged rule edit önce uygulanır, sonra siler — net effect "delete wins". Test #13'e bu invariant eklenmeli mi? Spec phase decision (önerme: ekle, küçük cost).
5. **`ensure_general_table` set_implicit(false) gerekiyor mu?** — toml_edit `DocumentMut::new()` üzerinden yaratılan Table'ın default'u implicit veya not. Spec phase tests confirm.
6. **`thiserror` zaten dep mi?** — `cargo tree | rg thiserror` post-spec verify. Eğer transitive değilse manuel Error+Display impl (`std::error::Error` + `fmt::Display`) — yeni dep eklenmiyor.

# tayf v0.3.0 — Genişletilmiş ANSI State Machine Tasarım Dokümanı

**Tarih:** 2026-05-23
**Kapsam:** v0.3.0 — `Pipeline`'ın mevcut TUI-mode state machine'ini genişletip OSC, SGR, ve non-CSI ESC sequence'leri eksiksiz parse etmesi; `respect_existing_colors` config field'ının line-level semantik ile devreye girmesi.
**Prereqs:** v0.2.4 yayınlanmış (✅ shipped). v0.3 umbrella vision (`2026-05-23-tayf-v0.3-vision.md`) onaylanmış.

v0.3 umbrella'sında v0.3.0 "VTE foundation" başlığıyla yazılmıştı. Brainstorming sırasında ortaya çıktı ki **mevcut `TuiModeSm` zaten DEC private mode set/reset'i tam doğru parse ediyor** (alt-screen 47/1047/1049, bracketed paste 2004, mouse 1000/1002/1003/1006). Eksik olan: OSC sequence handling, SGR varlık tespiti, non-CSI ESC sequence'leri. v0.3.0 bu üç kategoriyi mevcut SM'i genişleterek ekler — yeni dep getirmez. Başlık bu nedenle "VTE foundation"dan "Genişletilmiş ANSI State Machine"e güncellendi.

## 1. Vizyon

`src/pipeline.rs::TuiModeSm` v0.1'den beri çalışıyor ve dört TUI moduna doğru cevap veriyor. Ama parse ettiği sequence kategorisi çok dar — sadece `CSI ? Pm h/l`. Diğer her şey "Ground state'e at" politikasıyla işleniyor; bu da şu byte'ların **line buffer'a girip regex'lere maruz kalması** demek:

- **OSC sequence'ler** (`\e]2;title\a` window title, `\e]8;;url\a label \e]8;;\a` hyperlink, `\e]133;A\a` shell prompt marker, `\e]52;c;<base64>\a` clipboard). Bunlar bozulduğunda terminal anormal davranır, kullanıcı görür.
- **SGR sequence'leri** (`\e[31;1m`). Mevcut config field'ı `respect_existing_colors = true` parse ediliyor ama hot path'a girmiyor — tayf zaten renkli bir log satırının üstüne kendi SGR'lerini binmiş şekilde basabiliyor.
- **Non-CSI ESC sequence'leri** (`\eM`, `\e7`, `\e=` vd.). Tek-byte payload'lı; çoğu zaman zararsız ama `\e7` → byte stream'inde `7` rakamı olarak görünüp `ipv4`/`http_status` pattern'larına false-match çıkarabilir.
- **DCS / PM / APC** sequence'leri (`\eP...\e\\`, `\e^...\e\\`, `\e_...\e\\`). Modern terminallerde nadir ama `kitty` keyboard protocol query'leri, `tmux` passthrough kullanır.

v0.3.0 mevcut TuiModeSm'i tam-ANSI'a yakın bir parser'a çevirir: yukarıdaki dört kategoriyi doğru parse eder, byte'larını **line buffer dışında tutar**, terminale verbatim passthrough yapar. `respect_existing_colors` config field'ı line-level semantik ile devreye girer.

### Hedefler

- `Pipeline.feed` artık OSC/DCS/PM/APC payload'larını line buffer'a sokmaz; rules onlara maruz kalmaz.
- `respect_existing_colors = true` iken bir satırda halihazırda SGR varsa o satıra tayf rule uygulamaz.
- Non-CSI ESC sequence'leri (tek-byte payload'lı) byte stream'inden ayıklanır, regex'lere taşınmaz.
- SM 5 → 8-10 state'e büyür (ölçü brainstorming'de yaklaşık, implementation'da netleşir).
- Throughput regression < %20 (umbrella §4.2 bütçesi).
- Yeni dependency yok (CLAUDE.md + memory'deki dependency minimalism kuralı).

### Hedef olmayan (sonraki sub-version'lara veya v0.4+'a)

- **VTE crate entegrasyonu.** v0.3 umbrella'sında düşünüldü, brainstorming'de **mevcut SM'i genişletme** kararı verildi (Karar 1).
- **Segment-level `respect_existing_colors` semantiği** — SGR aralıklarını atla, default-state byte'lara rule uygula. v0.4'e ertelendi (Karar 2).
- **OSC 8 hyperlink label'ına rule uygulama** — OSC tüm payload'ı verbatim passthrough; label'a regex uygulamak v0.4+'da değerlendirilebilir (Karar 3).
- **CAN/SUB cancel byte handling** (0x18, 0x1A). Mevcut SM ESC ile resync ediyor; CAN/SUB ekstra resilience getirir ama YAGNI (Karar 4).
- **Otomatik bg detection** (`COLORFGBG` / OSC 11). v0.3.1.
- **Pattern polish** (URL trim, `git@host:path`, bare duration units). v0.3.2.
- **Escape hatches** (`--bypass`, `TAYF_DISABLE`). v0.3.3.

## 3. State machine — genişletilmiş şema

### 3.1 State listesi

Mevcut 5 state (Ground, EscSeen, Csi, Question, Digits) korunur. Yeni state'ler:

| State | Giriş tetiği | Çıkış tetiği | Davranış |
|---|---|---|---|
| `Osc` | `\e]` | `\x07` (BEL) veya `\e\\` (ST) | Payload byte'larını passthrough işaretler; line buffer'a yazılmaz |
| `OscEsc` | `Osc` içinde `\e` | `\` → Ground (ST tamamlanır); başka byte → EscSeen (lone ESC ile resync) | ST terminator'ünün ikinci byte'ını bekler |
| `EscFinal` | `\e` + tek-byte sequence başlatan byte değil; örn. `\e=`, `\eM`, `\e7`, `\e8`, `\eD`, `\eE`, `\eH`, `\eN`, `\eO`, `\e>` vs. | Bir sonraki byte (tüketilir) → Ground | Tek-byte payload'lı ESC sequence'leri için |
| `Dcs` | `\eP` | `\e\\` (ST) | OSC ile aynı: payload passthrough |
| `DcsEsc` | `Dcs` içinde `\e` | `\` → Ground; başka → EscSeen | ST terminator'ün ikinci byte'ı |
| `Pm` / `Apc` | `\e^` / `\e_` | `\e\\` | DCS ile aynı; ayrı state'ler çünkü test'lerde isimlendirme net olur |
| `Sgr` (Csi içinde substate) | `Digits` içinde `;` veya rakam (CSI parametre listesi) | `m` (final byte) → SGR konsume; başka final → `Digits` Csi davranışına dön | `m` final byte'ı görüldüğünde `line_has_sgr = true` flag set |

**Mevcut `Question/Digits` substate'leri** korunur — `CSI ? Pm h/l` ayrı bir path; SGR `CSI Pm m` paralel bir path. Pratik olarak Csi state'inde `?` görmek mod-set akışı, görmemek SGR/diğer akış.

### 3.2 Transition tablosu (özet)

```
Ground        + \e         → EscSeen
EscSeen       + [          → Csi
EscSeen       + ]          → Osc
EscSeen       + P          → Dcs
EscSeen       + ^          → Pm
EscSeen       + _          → Apc
EscSeen       + 0x30..0x7E (CSI'ye girmeyen single-byte) → EscFinal
EscSeen       + \e         → EscSeen (lone ESC resync)
EscSeen       + diğer       → Ground

Csi           + ?          → Question
Csi           + 0x30..0x3F (parametre) → Digits
Csi           + 0x40..0x7E (final byte) → final'a göre işle, Ground
                  - 'm' → SGR consume: line_has_sgr = true
                  - 'h'/'l' (CSI'de ? yoksa) → ignored, Ground
Digits/Question + h         → DEC mode set (TUI flag)
Digits/Question + l         → DEC mode reset (TUI flag)
Digits         + 'm'        → SGR consume: line_has_sgr = true
Digits         + diğer final → Ground (rule yok, ignored)

Osc           + 0x07 (BEL) → Ground
Osc           + \e         → OscEsc
OscEsc        + \          → Ground (ST tamamlandı)
OscEsc        + diğer       → EscSeen (lone ESC, OSC abort)

Dcs / Pm / Apc + \e        → DcsEsc / PmEsc / ApcEsc
DcsEsc        + \          → Ground
(diğerleri analojik)

EscFinal      + herhangi byte → Ground (1 byte payload consume)
```

### 3.3 `passthrough()` semantiği

Mevcut `TuiModeSm::passthrough() -> bool` "TUI bayrağı set mi?" demek. Genişletilmiş anlamda iki kontrat lazım:

- **`tui_mode_active() -> bool`** (eski adıyla `passthrough`): Alt-screen / bracketed paste / mouse modlarından biri aktif. Pipeline.feed bunu görünce satırlar değil, segment'ler halinde write-through yapar.
- **`in_terminal_sequence() -> bool`** (yeni): SM şu anda OSC/DCS/PM/APC/EscFinal/Csi/EscSeen state'inde — yani bir ANSI sequence'in **ortasında**. Pipeline.feed bunu görünce bytes line buffer'a giremez; verbatim çıkar.

Pipeline.feed mevcut "passthrough?" sorusunu `tui_mode_active() || in_terminal_sequence()` olarak genişletir.

## 4. Yeni davranışlar

### 4.1 OSC passthrough

OSC sequence başladığında (`\e]`) SM `Osc` state'ine geçer. Pipeline.feed bu state boyunca byte'ları doğrudan `out.write_all` ile yazar — line buffer'a sokmaz. Terminator (BEL veya ST) sonrası Ground'a döner. **Sonuç:** OSC 8 hyperlink, OSC 2 window title, OSC 0/1 icon title, OSC 133 shell prompt marker, OSC 52 clipboard — hepsi bozulmadan terminale ulaşır; URL'nin içindeki `https://...` substring'i regex'lere maruz kalmaz.

### 4.2 SGR-aware line flag

`Pipeline` struct'ına yeni alan eklenir:

```rust
pub(crate) struct Pipeline {
    sm: TuiModeSm,
    buffer: LineBuffer,
    rules: Arc<ArcSwap<Compiled>>,
    line_has_sgr: bool,                    // NEW
    respect_existing_colors: bool,          // NEW (config'ten gelir)
}
```

SM Csi state'inde `m` final byte'ı tükettiğinde flag set olur. `apply_rules` çağrılırken:

```rust
if self.respect_existing_colors && self.line_has_sgr {
    out.write_all(&line)?;          // verbatim passthrough
} else {
    apply_rules(&line, &self.rules, out)?;
}
self.line_has_sgr = false;          // reset for next line
```

`respect_existing_colors = false` (default v0.2 davranışı) iken flag tutulur ama kontrol skip — eski davranış byte-for-byte aynıdır.

### 4.3 Non-CSI ESC ve DCS/PM/APC passthrough

`\e=` (DECKPAM), `\eM` (RI), `\e7`/`\e8` (DECSC/DECRC), `\eD` (IND), `\eE` (NEL), `\eH` (HTS), `\eN`/`\eO` (SS2/SS3), `\eP...\e\\` (DCS), `\e^...\e\\` (PM), `\e_...\e\\` (APC) — hepsi `in_terminal_sequence()` true iken Pipeline.feed write-through yapar. **Hiçbiri line buffer'a girmez, regex'lere maruz kalmaz.**

DCS/PM/APC payload uzunluğu üzerinde explicit cap yok; passthrough byte'ları doğrudan `out` writer'ına gider, memory büyümez.

### 4.4 Config bağlama

`Pipeline::new` imzası genişler:

```rust
// Eski (v0.2):
pub(crate) fn new(rules: Arc<ArcSwap<Compiled>>) -> Self

// Yeni (v0.3.0):
pub(crate) fn new(rules: Arc<ArcSwap<Compiled>>, respect_existing_colors: bool) -> Self
```

Mevcut callsite `src/runtime.rs` (output thread spawn) güncellenir. Config'ten gelen değer `Tayf::run`'da okunur ve constructor'a geçirilir.

**Hot reload notu:** `respect_existing_colors` config field'ı reload'a göre değişebilir. Mevcut reload mekanizması sadece `Compiled` rule set'ini swap ediyor; `respect_existing_colors` flag'i Pipeline'a startup'ta gömülü. Hot reload + bu flag'i değiştirme **şu anki release scope'unda kapsamlı çözümlenmiyor**:

- Pipeline'ın `respect_existing_colors`'ı da Arc<AtomicBool> ile reload-aware yapabilirdik.
- Alternatif: Compiled struct'ına bu bool'u koyup ArcSwap üzerinden swap edebilirdik.

**Karar:** Şu sürümde `respect_existing_colors` startup-snapshot. Reload sırasında değer değişirse warning loglanır ama Pipeline davranışı eski değerle kalır. Bu kısıtlamayı README'de açıkça not edeceğiz; v0.3.3 (reload banner) sırasında atomic bool refactor'u değerlendirilir.

## 5. Pipeline.feed değişikliği

Mevcut akış (`src/pipeline.rs:180-215`):

```rust
pub(crate) fn feed<W: Write>(&mut self, chunk: &[u8], out: &mut W) -> std::io::Result<()> {
    let mut cursor = 0;
    while cursor < chunk.len() {
        let pass_before = self.sm.passthrough();
        let mut i = cursor;
        while i < chunk.len() {
            self.sm.step(chunk[i]);
            i += 1;
            if self.sm.passthrough() != pass_before { break; }
        }
        let segment = &chunk[cursor..i];
        cursor = i;
        // ... passthrough ise write_all, değilse line_buffer.feed
    }
    Ok(())
}
```

Yeni akış aynı şekil, sadece `passthrough()` çağrısı `tui_mode_active() || in_terminal_sequence()` olur. Ek bir koşul: SGR sequence'i Csi state'inde `m` ile bittiğinde flag set; bu Pipeline tarafından **read-after-step** olarak okunur.

```rust
// Pseudo (gerçek implementation Pipeline.feed içinde):
fn step_and_observe(&mut self, byte: u8) -> StepResult {
    self.sm.step(byte);
    if self.sm.consumed_sgr_this_step() {
        self.line_has_sgr = true;
    }
    StepResult { write_through: self.sm.is_write_through() }
}
```

`consumed_sgr_this_step()` SM'in step return value'sunu zenginleştirir. İki seçenek:

- **Seçenek A:** SM `step` return tipini `bool` → `StepEvent` enum'a çevir. Daha açık, ama tüm callsite'ları etkiler.
- **Seçenek B:** SM içinde transient `sgr_consumed: bool` flag tut, Pipeline her step sonrası okuyup reset etsin. Daha az API değişikliği.

**Önerim: Seçenek B** — mevcut TuiModeSm API'sını minimum bozar, Pipeline integration'ı temiz.

## 7. Güvenlik (CLAUDE.md §3)

### 7.1 Adversarial input

SM her byte'ta deterministik state transition yapar; allocation yok. Edge case'ler:

- **OSC içinde lone `\e`** (yani ST'in `\` byte'ı gelmeden başka `\e`): `OscEsc` state'inden çıkıp `EscSeen`'e dön, sequence abort. Mevcut "ESC resync" kuralının uzantısı.
- **Çok uzun OSC payload'ı**: payload byte'ları doğrudan stdout'a gidiyor; memory cap yok (line buffer 1 MiB cap'i devreye girmiyor). DoS riski: yok (yine de attacker terminal output'unu doğrudan stdout'a gönderebilir; tayf'ın işi durdurmak değil).
- **Truncate edilmiş sequence** (örn. `\e[?1049` arkasından EOF): SM Digits state'inde kalır. Pipeline drain ederken sequence-state'inde kalan byte'lar var mı? Var ama drain artık `apply_rules` çağırmıyor; in_terminal_sequence true olduğu için bytes verbatim çıkmıştı zaten.

### 7.2 Memory

- SM state pointer: 1 enum (8 byte). `accum: u32` (4 byte). `flags: u32` (4 byte). `sgr_consumed: bool` (1 byte). Total ~20 byte. Allocation yok.
- Pipeline alanları: `respect_existing_colors: bool` ve `line_has_sgr: bool` her biri 1 byte.

### 7.3 No new attack surface

- Yeni dep yok → cargo audit ve cargo deny aynı kalır.
- Yeni FS path yok.
- Yeni public API yok (`Pipeline::new` imza değişti ama `pub(crate)` olduğu için dış consumer yok).
- `Error` enum'u değişmedi.

### 7.4 Performans güvenliği

Hot path'da byte başına ek iş:
- Mevcut: ~10ns/byte (TuiModeSm step + match expression).
- Yeni: ~12-15ns/byte (3 yeni state, ek match arm'leri). 
- 500 MB/s throughput'ta her byte için 15ns = 7.5 Gflop iş; modern CPU'da kolay karşılanır.
- Umbrella §4.2 bütçesi: < %20 regression. Benchmark `benches/throughput.rs` ile doğrulanır.

## 1. Vizyon

### 1.1 Kapsam A — Otomatik bg detection (best-effort starting-point default)

**Kabul ediyoruz:** Modern terminallerin temaları "light" ve "dark" iki kovaya sığmıyor. Solarized Dark, Nord, Gruvbox Dark, Dracula, Tokyo Night, Catppuccin Mocha — hepsi "dark" ailesinde ama bg tonları (deep blue, dark gray, brownish-black, near-black) ve onlara yakışan FG kontrast renkleri ayrı. v0.2.3'te ship'lediğimiz `dark.toml` ve `light.toml` "tüm dark/light terminallere uyar" iddiası taşımıyor; sadece "default-ish dark/light için makul kontrast veren built-in stil setleri." Bu **sınırlı bir başlangıç**, kapsayıcı bir çözüm değil. Asıl ihtiyaç — kullanıcının kendi paletini terminaline göre seçebilmesi — disk-based custom themes (v0.3.4) ve user-config rules ile karşılanır.

v0.3.1'in auto bg detection'ı bu çerçevede konumlanıyor: **iki kovadan birini seçmek için convenience default**. v0.2.3 light/dark preset'leri zaten ship oldu, kullanıcı bunlardan birini `--theme <name>` veya `[general] theme = "<name>"` ile manuel seçiyor; light terminal kullanıcısı her tayf çağrısında `--theme light` yazmak zorunda. v0.3.1 bunu otomatikleştirir — ama **best-effort hint olarak, authoritative seçim olarak değil.**

Startup'ta sıralı detection:

1. **`COLORFGBG` env var** (rxvt/urxvt/eski xterm convention) — `fg;bg` formatında bg ANSI 16-color index; `< 8` koyu, `>= 8` açık.
2. **OSC 11 query** (`\e]11;?\e\\`) — `/dev/tty` üzerinden gönder, `select(2)` ile 100 ms timeout'lu oku, response parse et (`\e]11;rgb:RRRR/GGGG/BBBB\e\\` veya BEL terminated), Rec. 601 weighted luminance hesapla, threshold 0.5 ile karar ver.
3. **Fallback** — `dark`.

Detection sonucu, **kullanıcı theme'i explicit olarak set etmediyse** uygulanır:

- CLI `--theme <name>` set ise → detection hiç çalışmaz; CLI kazanır.
- `[general] theme = "<name>"` set ise → detection hiç çalışmaz; config kazanır.
- Her ikisi de set değilse VE `apply_colors == true` (stdout TTY + `COLORDEPTH != None` + `--no-color` yok) → detection çalışır, sonuç `effective_theme`'e doldurulur.
- `apply_colors == false` ise → detection skip; theme zaten output stream'inde görsel bir etki yapmaz.

**Doğru beklenti seti (README + CHANGELOG'da explicit'lenir):** Detection sonucu kullanıcının teması "default-ish light" veya "default-ish dark" ise muhtemelen tatmin edici görünür. Solarized Dark / Nord / Gruvbox gibi spesifik bir paletse, built-in `dark` preset'i kontrastı doğru ama ton uyumunu garantilemez — kullanıcı `[[rules]]` ile spot ayarları yapabilir veya v0.3.4 sonrası kendi disk theme'ini tanımlayabilir. **Detection bir kestirme yol, bir bağlayıcı seçim değil.**

### 1.2 Kapsam B — I4 fix (cap-fire-in-string-state)

v0.3.0 `AnsiSm`'i 4 KiB `SEQUENCE_BYTES_CAP` ile defansif kapatıyor. Cap fire ederse SM `Ground`'a düşer ve byte `Data` event olarak Pipeline'a verilir. **Eksiklik:** SM `OscString` / `DcsPassthrough` / `SosPmApcString` (veya peek-ahead `OscEsc` / `DcsEsc` / `SosPmApcEsc`) state'inde iken cap fire ederse, Pipeline o ana kadar `StringPayloadByte` event'leriyle payload byte'larını direkt stdout'a yazmış oldu — terminal `\e]` introducer'ını gördü ama terminator'ü (`\e\\` veya BEL) **görmedi**. Modern terminaller (xterm, iTerm2, kitty, foot) unterminated string sequence'i bekledikleri kendi internal cap'lerine kadar yutmaya devam ederler.

Bunun adversarial sonucu: attacker, kullanıcının PTY child stream'ine 4 KiB+ uzunluğunda bir OSC payload (terminator olmadan) gönderirse, tayf'ın `\n` veya başka bir kontrol byte'ı görmesi terminator'ü oluşturmaz; terminal payload yutmayı sürdürür. Şimdiki gerçek shell output'unun ilk N byte'ı (terminalin OSC cap'i tükenene kadar) görsel olarak yutulur → kullanıcı "tayf ekranı yedi" der.

**Fix:** SM cap fire ederken prior state bir string-state ise, yeni `StepEvent::ForceStringTerminate` variant'ı emit eder. Pipeline bu event'i alınca `\e\\` (7-bit ST, 2 byte: ESC 0x1B + backslash 0x5C) byte'larını **stdout'a write_all** ile yazar — terminal sequence'i prompt-and-go ile kapatır. SM zaten cap-fire branch'inde `Ground`'a resetlenmiştir; Pipeline cap-trigger byte'ını SM'e re-step eder, byte normal classification (Data/SequenceByte/...) ile yeniden işlenir.

### 1.3 Hedefler

- Default-ish light/dark terminal kullanıcısı için: `--theme` yazma gereksinimi otomatize edilir. Zero-config'te `dark` veya `light` preset uygulanır (binary best-guess).
- Detection 100 ms wall-clock cap içinde sonuçlanır; başarısız olursa sessizce `dark` fallback'e düşer.
- Detection tamamen opsiyonel ve override edilebilir: explicit CLI/config theme her zaman kazanır.
- README + CHANGELOG'da limitations dürüstçe documente edilir: "best-effort starting-point; for tighter match, define your own theme rules — disk themes shipping in v0.3.4."
- I4 fix yalın: SM'e tek yeni event variant; Pipeline'a tek match arm; mevcut hot path latency'sine ölçülebilir etki yok.
- Yeni dep yok.
- Public API değişmez.
- Backward compat: v0.3.0 config dosyaları (v0.2 dahil) shimless okunur.

### 1.4 Hedef olmayan (sonraki sub-version'lara veya v0.4+'a)

- **Modern terminal teması çeşitliliğini tam karşılamak.** v0.3.1 binary (dark/light) bir hint sağlar; Solarized/Nord/Gruvbox/etc gibi spesifik paletlerin tam uyumu **v0.3.4 disk themes**'in işidir.
- **Detection sonucunu kullanıcının seçtiği custom theme name'e map'lemek.** v0.3.1 hardcoded `"light"` ve `"dark"` döner. v0.3.4 disk themes ship olduğunda, kullanıcı talebine göre potansiyel `[general] light_theme = "<name>"` / `dark_theme = "<name>"` config field'ları eklenebilir — v0.3.1 scope'unda DEĞİL, sadece API extensibility için bilinçli açık bırakıldı.
- **Detection result'ın hot reload sırasında re-resolve edilmesi.** Theme contract umbrella'da pinlendi: theme = startup snapshot. Hot reload theme'i mid-session değiştirmez. Bg detection da startup-only.
- **`auto_theme = false` config field'ı veya `TAYF_NO_AUTO_THEME` env var.** YAGNI; mevcut "explicit theme = opt-out" yeterli.
- **"Medium" theme veya luminance fuzzy zone.** v0.2.3 sadece light/dark ship etti; medium yok.
- **Detection re-trial logic (timeout sonrası retry).** Best-effort tek shot. Miss → fallback dark; kullanıcı `--theme light` yazabilir.
- **DCS query truncate (OSC 11 alternatifi).** Sub-set; OSC 11 universal.
- **OSC 10 (foreground color) query.** v0.3.1 sadece bg'ye karar veriyor. Foreground gerekirse v0.4+'a.
- **Symmetric cap-fire API (her iki cap-fire path'i için aynı event şekli).** Existing v0.3.0 davranışı (`Data` döner) korunur; sadece string-state path'ı genişletilir.

### 1.5 Framing — neden binary detection ship ediyoruz?

"Light vs dark" iki kovaya zorunlu sığdırma fundamentally lossy. Aynı bg'ye iki kullanıcı farklı palet tercih edebilir; aynı "dark" etiketi altında onlarca farklı ton var. Buna rağmen v0.3.1'in detection feature'ını ship etmemizin nedeni:

1. **Concrete win for the common case.** Çoğu kullanıcı default-ish dark veya default-ish light terminal kullanır (macOS Terminal default, GNOME Terminal default, Windows Terminal default, vs.). Bu kümeler için "yanlış kontrast yönü" (light text on light bg) ciddi UX kazasıdır. Binary detection bu kazayı zero-config önler.
2. **Cost is minimal.** Implementation ~200 satır + 12 unit test; runtime cost startup'ta tek shot ≤ 100 ms. Net dependency yok. Maintenance burden düşük.
3. **Doesn't preclude richer customization.** Detection ile user-config rules veya v0.3.4 disk themes ortogonal; biri diğerinin önünü kapatmıyor.

Bu pozisyonu README'de **explicit'lenir** — kullanıcının detection'ı "yetkili tema kararı" sanmasına izin vermeyiz. "Bu bir starting-point. Tam kontrol için override et veya kendi paletini tanımla."

## 3. Bg detection altsistemi (Kapsam A)

### 3.1 Yeni modül: `src/bg_detect.rs`

Module-level doc-comment'ı: amaç, public API yüzeyi, OSC 11 referansı (xterm ctlseqs `Operating System Commands` bölümü), Rec. 601 luminance formülü kaynağı, tmux passthrough escape format'ı. CLAUDE.md §2 mandate.

```rust
//! Background color detection for automatic light/dark theme resolution.
//!
//! Startup-only resolver: COLORFGBG env var → OSC 11 query → dark fallback.
//! See spec §3 for the full algorithm and timing budget.
//!
//! Reference: xterm Operating System Commands ("OSC") — sequence 11 reports
//! the terminal's default background color via the response
//! `\e]11;rgb:RRRR/GGGG/BBBB\e\\` (or BEL-terminated). Rec. 601 weighted
//! luminance (Y = 0.299·R + 0.587·G + 0.114·B) decides light vs dark with
//! threshold 0.5.
//!
//! Termios handling: the OSC 11 path opens `/dev/tty`, snapshots termios,
//! switches to raw mode, queries, reads with `select(2)` timeout, then
//! restores termios — all under an RAII guard so any error path (including
//! panic via `std::panic::set_hook` — installed by `tty_guard.rs` and
//! shared, see §3.5) restores the terminal.
```

### 3.2 Public API yüzeyi

```rust
/// Resolved background theme. Maps directly to v0.2.3 preset theme names:
/// `BgTheme::Light` → `"light"`, `BgTheme::Dark` → `"dark"`.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) enum BgTheme {
    Light,
    Dark,
}

impl BgTheme {
    /// String identifier matching `themes::load` registry. Stable.
    pub(crate) fn as_theme_name(self) -> &'static str {
        match self {
            BgTheme::Light => "light",
            BgTheme::Dark => "dark",
        }
    }
}

/// Resolve the effective background theme by trying detection paths in
/// order. Never panics. Falls back to `BgTheme::Dark` on any failure.
///
/// Time budget: ≤ 100 ms wall clock. Spec §3.4 (OSC 11 timeout).
///
/// Side effects: may briefly toggle termios on `/dev/tty` if it reaches
/// the OSC 11 path. All paths restore termios on return.
pub(crate) fn resolve() -> BgTheme {
    if let Some(t) = detect_from_colorfgbg() {
        crate::log::debug_msg!("bg_detect: colorfgbg -> {t:?}");
        return t;
    }
    if let Some(t) = detect_from_osc11() {
        crate::log::debug_msg!("bg_detect: osc11 -> {t:?}");
        return t;
    }
    crate::log::debug_msg!("bg_detect: fallback -> Dark");
    BgTheme::Dark
}
```

### 3.3 COLORFGBG path — saf fonksiyon

```rust
/// Parse the COLORFGBG environment variable.
///
/// rxvt / urxvt format: `fg;bg` where bg is an xterm color number 0..15.
/// Some implementations include a third field (`fg;bd;bg`) for default-bd
/// status; we accept both. Value `default` is rejected (no useful signal).
///
/// Returns:
/// - `Some(Light)` if bg index in 8..=15
/// - `Some(Dark)`  if bg index in 0..=7
/// - `None` if env var unset, malformed, contains `default`, or out of range
fn detect_from_colorfgbg() -> Option<BgTheme> {
    let raw = std::env::var("COLORFGBG").ok()?;
    parse_colorfgbg(&raw)
}

fn parse_colorfgbg(s: &str) -> Option<BgTheme> {
    // Last field is the bg index. Accept "fg;bg" or "fg;bd;bg".
    let bg = s.split(';').last()?;
    if bg.eq_ignore_ascii_case("default") {
        return None;
    }
    let n: u8 = bg.trim().parse().ok()?;
    if n > 15 {
        return None;
    }
    if n < 8 { Some(BgTheme::Dark) } else { Some(BgTheme::Light) }
}
```

### 3.4 OSC 11 path — query + timeout + parse

```rust
/// Send OSC 11 query to /dev/tty and parse response. Returns None on:
/// - stdout not a TTY (no terminal to query)
/// - $STY set (GNU screen, passthrough unreliable)
/// - /dev/tty open failure
/// - termios snapshot/raw failure
/// - write or read I/O error
/// - timeout (100 ms)
/// - malformed response
///
/// Side effects:
/// - temporarily switches /dev/tty to raw mode (RAII restored on return)
/// - installs a process-wide panic hook for the raw window (see §6.3 —
///   needed because `panic = "abort"` in release profile prevents Drop
///   from running on panic)
/// - on successful response read, drains remaining /dev/tty input
///   non-blocking until EAGAIN, then writes `\r\e[K` to wipe any potential
///   echo of the query by terminals that don't understand OSC 11
fn detect_from_osc11() -> Option<BgTheme> {
    use std::env;
    if env::var_os("STY").is_some() {
        return None;
    }
    if !crate::terminfo::stdout_is_tty() {
        return None;
    }

    let query: &[u8] = if env::var_os("TMUX").is_some() {
        // tmux passthrough wrapper. Requires `allow-passthrough on` in tmux
        // 3.3+ (default off); tmux ≤3.2 enables it by default. When disabled,
        // the wrapped query is silently dropped → read times out → fallback.
        // Format: \e P t m u x ; <inner-with-ESC-doubled> \e \\
        // Inner: \e]11;?\e\\ → after ESC-doubling: \e\e]11;?\e\e\\
        b"\x1bPtmux;\x1b\x1b]11;?\x1b\x1b\\\x1b\\"
    } else {
        b"\x1b]11;?\x1b\\"
    };

    let tty = open_dev_tty().ok()?;
    let fd = tty.as_raw_fd();
    let _guard = TtyRawGuard::engage(fd).ok()?;
    write_all_with_timeout(fd, query, OSC11_WRITE_TIMEOUT).ok()?;
    let response = read_until_terminator(fd, OSC11_READ_TIMEOUT).ok()?;
    drain_remaining(fd); // unbounded non-blocking; consumes any delayed response bytes
    suppress_query_echo(fd); // write \r\e[K to wipe potential literal echo of the query
    parse_osc11_response(&response)
}

const OSC11_WRITE_TIMEOUT: Duration = Duration::from_millis(50);
const OSC11_READ_TIMEOUT: Duration = Duration::from_millis(100);
const OSC11_RESPONSE_CAP: usize = 128; // hard cap on response buffer
```

**Termios management** — kendi RAII guard'ı, mevcut `tty_guard::TtyGuard`'tan ayrı **ve** kendi panic hook'unu install eder:

```rust
/// Short-lived raw-mode guard for the bg-detect path. Separate from the
/// main `tty_guard::TtyGuard` because bg-detect runs BEFORE the main
/// guard engages (see §3.6 — placement in Tayf::run).
///
/// Lifecycle:
///   engage: tcgetattr snapshot → install panic hook → cfmakeraw →
///           tcsetattr(raw)
///   drop:   tcsetattr(snapshot) → clear panic-hook slot
///
/// **Panic safety:** the release profile uses `panic = "abort"`
/// (Cargo.toml), so Drop does NOT run on panic. We install a
/// `std::panic::set_hook` BEFORE the `tcsetattr(raw)` call; the hook
/// restores /dev/tty's termios on panic before the runtime aborts. The
/// hook checks a `OnceLock<Mutex<Option<(RawFd, Termios)>>>` for the
/// snapshot. `engage` populates the slot; `drop` clears it.
///
/// This is parallel-but-not-shared with `tty_guard::install_panic_hook`
/// (which restores stdin's termios with the main TtyGuard's snapshot).
/// Both hooks chain via `take_hook`/`set_hook`; the chained hooks each
/// check their own slot, restoring only when their slot is non-empty.
/// In normal operation, the bg-detect slot empties before the main guard
/// engages, so only the main guard's hook does work on a later panic.
struct TtyRawGuard {
    fd: std::os::fd::RawFd,
    original: nix::sys::termios::Termios,
}
```

The `RawFd` (a `Copy` integer) eliminates the `'a` lifetime that would otherwise tie the guard to the `File` borrow — the guard's restore path only needs the fd. The `File` (owning the fd) is held in the calling function's local; the guard's `Drop` runs while that local is still alive (drop-order semantics).

**Open `/dev/tty`** — `std::fs::OpenOptions::new().read(true).write(true).open("/dev/tty")`. Stdin yerine `/dev/tty` çünkü stdin redirect olabilir (`tayf < input.txt`). `/dev/tty` syscall mekanizması process'in controlling terminal'ini her durumda verir. Spawnlanan PTY child kendi slave PTY'sini alır; `/dev/tty` ile karışmaz.

**Write with timeout** — `nix::poll::poll` ile fd write'ı bekle, timeout aşılırsa abort. Genelde 0 ms'de tamamlanır (kernel buffer write).

**Read with timeout** — `nix::poll::poll` ile read fd ready bekle, 100 ms cap. Her read syscall sonrası response buffer terminator için byte-wise scan edilir (BEL = 0x07, 7-bit ST = ESC + backslash, 8-bit C1 ST = 0x9C). Buffer `OSC11_RESPONSE_CAP` (128 byte) cap'ine ulaşırsa abort (defansif).

**Drain remaining** — `read_until_terminator` başarılıysa, sonraki shell session'ına byte sızmasını önlemek için `/dev/tty`'yi non-blocking modda EAGAIN/EWOULDBLOCK gelene kadar drain et. Buffer boyutu küçük (typical kernel TTY buffer 4 KiB), unbounded loop pratikte birkaç syscall'da biter. **Yalnızca response başarılıysa drain çalışır** — başarısız read durumunda kullanıcının pre-typed keystroke'larını yutmak istemiyoruz.

**Echo suppression** — Eski terminaller (DEC VT420, bazı Windows console host versiyonları) OSC 11 query'sini literal text olarak ekrana basabilir. `\r\e[K` (CR + EraseInLine) bg-detect dönüşünden hemen önce yazılır → tayf shell'i spawn etmeden önce ekranın o satırı temizlenir. Bu, kullanıcının dış shell prompt'ını silebilir ama tayf saniye-altı sonra kendi shell'ini spawn ediyor → prompt yenilenir, kullanıcı sızıntıyı görmez. Net: defansif, low-cost.

### 3.5 Response parser

Byte-wise parsing — `std::str::from_utf8` ÇAĞRILMAZ. Terminal response'ları 7-bit ASCII alfabesinde (printable + ESC + BEL + backslash) ama bazı response'lar 8-bit C1 ST (0x9C) terminator içerir, ki bu 0x9C tek başına invalid UTF-8 continuation byte'tır. UTF-8 kontrolü yapsaydık 8-bit C1 ST kullanan terminalleri sessizce reject ederdik — bu correctness regression.

```rust
/// Parse OSC 11 response: `\e]11;rgb:RRRR/GGGG/BBBB<terminator>` or
/// `\e]11;rgb:RR/GG/BB<terminator>` where terminator is one of:
/// - BEL (0x07)
/// - 7-bit ST (ESC = 0x1B, backslash follows as part of `\e\\`)
/// - 8-bit C1 ST (0x9C)
///
/// Some terminals (notably tmux relays) strip the leading ESC. We accept
/// both forms by looking for the byte sequence `]11;rgb:`. Byte-wise
/// parsing throughout — no UTF-8 dependency.
fn parse_osc11_response(bytes: &[u8]) -> Option<BgTheme> {
    let prefix = b"]11;rgb:";
    let i = bytes.windows(prefix.len()).position(|w| w == prefix)?;
    let payload = &bytes[i + prefix.len()..];
    // payload is: e.g. b"RRRR/GGGG/BBBB\x1b\\..." or b"RR/GG/BB\x07..."
    let end = payload
        .iter()
        .position(|&b| matches!(b, 0x07 | 0x1B | 0x9C))
        .unwrap_or(payload.len());
    let triple = &payload[..end];
    let mut parts = triple.split(|&b| b == b'/');
    let r = parse_hex_channel(parts.next()?)?;
    let g = parse_hex_channel(parts.next()?)?;
    let b = parse_hex_channel(parts.next()?)?;
    if parts.next().is_some() {
        return None;
    }
    Some(luminance_to_theme(r, g, b))
}

/// Parse a hex channel of 1..=4 ASCII hex nibbles to a 0.0..=1.0 float.
/// `RR` → 0xRR / 0xFF; `RRRR` → 0xRRRR / 0xFFFF. Both forms scale to [0,1].
fn parse_hex_channel(bytes: &[u8]) -> Option<f32> {
    let len = bytes.len();
    if !(1..=4).contains(&len) {
        return None;
    }
    // Channel bytes are guaranteed ASCII hex digits if valid; from_utf8 here
    // is safe (ASCII subset of UTF-8) and bounded to 4 bytes.
    let s = std::str::from_utf8(bytes).ok()?;
    let n = u32::from_str_radix(s, 16).ok()?;
    let max = match len {
        1 => 0xF,
        2 => 0xFF,
        3 => 0xFFF,
        4 => 0xFFFF,
        _ => unreachable!("len bounded by the early check above"),
    };
    #[allow(clippy::cast_precision_loss)]
    // reason: max is at most 0xFFFF (65535), well within f32 mantissa range
    Some(n as f32 / max as f32)
}

/// Rec. 601 weighted luminance with threshold 0.5 (inclusive → Light).
/// The boundary direction (`>=` not `>`) ensures deterministic mapping
/// when float arithmetic lands exactly on 0.5 — IEEE 754 sums of
/// 0.299, 0.587, 0.114 are not guaranteed to be exactly 1.0, so an
/// inclusive boundary matches the test cases robustly.
fn luminance_to_theme(r: f32, g: f32, b: f32) -> BgTheme {
    let y = 0.299 * r + 0.587 * g + 0.114 * b;
    if y >= 0.5 { BgTheme::Light } else { BgTheme::Dark }
}
```

### 4.4 Edge case'ler

**TUI mode aktifken cap fire?** Pipeline byte'ı stdout'a yazdı (TUI passthrough); sonra SM step ForceStringTerminate döndü → synthetic ST emit edilir → terminal sequence'i kapatır. Re-step gerekmiyor çünkü byte stdout'a zaten yazıldı, line_buffer'a girmiyor. Bu, **senior review tarafından flagged tmux-running-inside-tayf-emits-large-OSC-52 senaryosunu** kapsar.

**Pipeline.feed yarıda kalırsa (örn. write error)?** Mevcut `?` propagation kullanılır. SM resetlendi (cap-fire branch zaten resetledi), Pipeline `sequence_scratch` boş (string-state cap fire'ında scratch zaten kullanılmıyordu, payload byte'ları doğrudan stdout). Sonraki `feed` çağrısı temiz başlar.

**`flush_partial` çağrısı cap-pending durumda?** v0.3.0'ın `flush_partial` semantiği: scratch'te byte varsa line_buffer'a aktar. Cap-fire string-state durumunda scratch boş (string payload scratch kullanmıyor) → `flush_partial` no-op. Drain path etkilenmez.

## 6. Güvenlik (CLAUDE.md §3 mandate)

### 6.1 Adversarial input — bg detection

- **OSC 11 response stuck / malformed.** `read_until_terminator` 100 ms cap'inde abort eder. Buffer `OSC11_RESPONSE_CAP` (128 byte) cap'i — büyük response (örn. attacker /dev/tty'ye terminal taklit ederek 1 MB veri push'larsa) cap'te durur. `parse_osc11_response` malformed input'a `None` döner.
- **OSC 11 stuck mid-write.** `write_all_with_timeout` 50 ms cap'inde abort eder. Kernel buffer doluysa veya tty kontrol stream'i blokeli ise abort.
- **`/dev/tty` permission denied.** `open_dev_tty` `Err` döner; `detect_from_osc11` `None` döner; fallback dark.
- **Termios snapshot failure.** RAII guard engage `Err` döner; detection fonksiyonu `None` döner; fallback dark. Termios state hiç değişmedi → güvenli.

### 6.2 Adversarial input — I4 fix

- **Attacker 4 KiB OSC payload (terminator yok).** Cap fire → SM ForceStringTerminate → Pipeline ST emit → terminal sequence'i kapat. Test §7.2'de coverage.
- **ST emit'in kendisi adversarial olabilir mi?** ST byte'ları (`\e\\`) sadece string state'i kapatır; başka bir state'i etkilemez. Sequence injection riski yok.
- **TUI mode aktifken cap fire?** §4.4 analizinde detaylı; pratik ulaşılamaz, ek defansiyel davranış gereksiz.

### 6.3 Termios restoration paths (CLAUDE.md §3 — terminal state corruption)

Bg detection raw mode toggle yapar; restore garantili olmalı. **Kritik gerçek:** `Cargo.toml` `[profile.release]` `panic = "abort"` set ediyor. Release build'de panic = abort means unwinding YAPILMAZ → `Drop` impl'leri panic'te ÇALIŞMAZ. Bu, v0.1 spec'inden beri bilinen bir gerçek (`docs/superpowers/plans/2026-05-21-tayf-v0.1.md:172` referansı) ve `tty_guard::install_panic_hook` zaten bu nedenle var.

- **Normal return.** `TtyRawGuard::drop` `tcsetattr(snapshot)` çağırır.
- **Error path (`Result::Err`).** `?` propagation guard'ı düşürür; Drop çalışır.
- **Panic (release build, `panic = "abort"`).** Drop ÇALIŞMAZ. Çözüm: bg_detect kendi panic hook'unu install eder.

**Panic hook mekanizması:**

`TtyRawGuard::engage(fd)` aşağıdaki sırayla işler:
1. `tcgetattr(fd)` → snapshot Termios.
2. Process-wide `OnceLock<Mutex<Option<(RawFd, Termios)>>>` slot'una `(fd, snapshot)` yaz.
3. `std::panic::set_hook` çağır ile `take_hook()` + chaining: panic ettiğinde, slot'tan `(fd, snapshot)`'ı oku, slot non-empty ise `tcsetattr(fd, snapshot)` çağır, sonra önceki hook'u zincir et. Hook bir kez install edilir (`Once::call_once`).
4. `cfmakeraw` + `tcsetattr(fd, raw)`.

`TtyRawGuard::drop`:
1. `tcsetattr(fd, snapshot)` — `let _ = ...` ile error silently ignore (`tty_guard::Drop` pattern mirror; restore başarısız olursa terminal zaten kaybedilmiş, ek bir şey yapmak yok).
2. Process-wide slot'u temizle (`*g = None`) → sonraki panic hook çağrısı no-op.

`tty_guard::install_panic_hook` ile **paralel-ama-paylaşılmayan** bir hook chaini. İki ayrı `OnceLock`:
- `tty_guard::PANIC_RESTORE_STATE` — stdin termios snapshot'ı.
- `bg_detect::PANIC_RESTORE_STATE` — /dev/tty termios snapshot'ı.

Hook chain (last-installed-runs-first, tüm hooks çalışır):
- bg_detect hook → kendi slot'unu kontrol et, non-empty ise restore /dev/tty.
- tty_guard hook → kendi slot'unu kontrol et, non-empty ise restore stdin.
- Default hook (backtrace yaz).

Normal akışta: bg_detect engage edip return ederken slot'unu temizler → sonraki panic'te bg_detect hook no-op. Aynı zamanda tty_guard engage etmiş ise stdin restore eder.

**Implementation note:** Hook install order önemli — bg_detect ÖNCE install eder (Tayf::run'da bg_detect TtyGuard'dan önce çalışıyor). `set_hook` `take_hook` ile zincirlediği için ikinci `install_panic_hook` çağrısı bg_detect'in hook'unu wrap eder. Doğru order.

**`unwind` (debug build) durumu:** Debug build'de panic unwinding yapar; `Drop` çalışır; hook + Drop ikisi de restore'u dener. İdempotent — `tcsetattr` aynı snapshot'la iki kez çağrılabilir, sorun değil.

### 6.4 Stdin drain ve race safety

OSC 11 response 100 ms içinde gelmezse timeout. Ama response 100 ms+ sonra gelirse `/dev/tty` buffer'ına düşer. Bu byte'lar PTY child stdin'ine sızar mı?

- Detection PTY spawn'dan ÖNCE çalışır → `runtime::run` henüz başlamadı → PTY master/slave henüz tahsis edilmedi.
- Bg detection function dönüşünden sonra `read_until_terminator` exit etti → `select`/`poll` artık tty fd'yi dinlemiyor.
- `drain_remaining` non-blocking loop ile up to 256 byte tüketir; bu byte'lar düşürülür.
- TtyGuard engage olduğunda stdin (process'in standard fd 0) raw mode'a alınır. Stdin'e gelen byte'lar runtime'ın input thread'ine pipe edilir. **Önemli:** `/dev/tty` ve `STDIN_FILENO` farklı fd'lerdir; her ikisi de aynı controlling terminal'e bağlıdır ama kernel buffer'ları ayrıdır.

Sonuç: drain'i `/dev/tty` fd'sinde yapmak yeterli. `STDIN_FILENO`'da delayed response yok çünkü query `/dev/tty`'ye gitti; response da `/dev/tty`'den okundu. STDIN buffer pristine.

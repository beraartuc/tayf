# tayf v0.12.0 — Profile rework (sub-project C)

**Status:** approved design, **rev2 (2026-06-02)** — parallel spec review folded
(see §13). Built on [[project-v0-12-0-shipped]] (sub-project A) and
[[project-v0-12-0-b-shipped]] (sub-project B), both on local `main`, unpushed
(HEAD `83dc72c`).

**Goal:** Make tayf "just work" for domain output (AWS / Docker / Kubernetes)
without making the user opt into a profile first, and re-cast the *profile*
feature from a fixed domain bundle into a **personal, switchable preset** of
which rules are active and what color each rule has.

---

## 1. Context & motivation

This is **sub-project C of the three-part v0.12.0 effort** (see
[[project-v0-12-0-shipped]]):

- **A — First-run & `init`** (shipped to local `main`).
- **B — TUI UX & polish** (shipped to local `main`).
- **C — Profile rework (this spec).**

A, B, and C land directly on `main` (no feature branches) and ship as a single
`v0.12.0` release: pushed together once C is done, with one `Cargo.toml` bump
(`0.11.0` → `0.12.0`) + tag at that joint push. This spec is written and
committed during development, then removed from `HEAD` before the joint push —
the same pattern A and B used. History keeps the design; `HEAD` stays clean.

### 1.1 The pivot (why this is not "composable profiles")

B's spec forward-pointed to C as "user-centric *composable* profiles" (opt-in
rule-packs). Brainstorming on 2026-06-02 rejected that framing. The decisive
observation: **nobody runs `tayf` and then opens the config to select the `aws`
profile before doing AWS work** — they just run their command. Opt-in friction
defeats the purpose of a colorizer.

The fix is to **promote the FP-safe domain rules into the built-in catalog** so
they fire by default, and to **retire the embedded profile library** entirely.

The one hard constraint is the project's built-in pattern bar
([[feedback-builtin-pattern-bar]]): a built-in must be ~zero-false-positive,
shape-unique, and prose-immune, because it is on for *everyone*. Auditing the
six domain rules against that bar:

| Rule | FP risk | Default-enabled built-in? |
|------|---------|---------------------------|
| `arn` | very low — literal `arn:aws` prefix, prose-immune | yes |
| `instance_id` | low — `i-` + exactly 17 hex | yes |
| `pod_name` | low–medium — double-hash suffix, base32 (no vowels) | no (ships, opt-in) |
| `image_tag` | medium — has FP guards (host:port, JSON, module:line) | no (ships, opt-in) |
| `region` | low FP, **dated 34-entry enum snapshot** (see §3.4) | no (ships, opt-in) |
| `container_id` | **high** — 12-hex collides with git short hashes everywhere | no (ships, opt-in) |

All six patterns are preserved (no domain value lost), but only the two
slam-dunks are on by default. The other four ship as **default-disabled
built-ins**, available to anyone via the new per-rule enable toggle. This
defuses the `container_id` git-hash landmine *without* a rule-pack mechanism,
and showcases the enable/disable feature.

The FP claim for the two always-on rules was verified empirically against
adversarial prose during review (§13): `arn:aws` rejects `warn:aws` / `alarm:aws`
/ `modern:aws` (word-boundary + literal `arn`); `\bi-[a-f0-9]{17}\b` rejects
`multi-…`, `wifi-…`, `i-beam`, `i-3`, 16/18-hex, and uppercase hex.

### 1.2 What "profile" means now

A profile is no longer a domain bundle. A profile is a **named, switchable
preset = {which rules are active, and each rule's color/style}**, built on top
of the built-in substrate. `config.toml` *is* the default profile; named
profiles are alternative presets the user creates and switches between.

---

## 2. Core model

Three rules govern the model:

1. **`config.toml` is the DEFAULT profile.** Its `[general]` and `[[rules]]`
   are unchanged → zero migration for existing users.
2. **Named profiles** live at `~/.config/tayf/profiles/<name>.toml` and use the
   **same `[[rules]]` schema** as `config.toml`. They are selected with the
   `--profile <name>` flag or `[general] profile = "<name>"`.
3. **Replace semantics.** When a named profile is active, its `[[rules]]` are
   used *instead of* `config.toml`'s `[[rules]]`. Built-ins remain the
   **substrate** in every profile (a profile enables/disables and recolors them
   and adds user patterns on top). `[general]` (theme, banner, active-profile
   pointer, …) always comes from `config.toml`.

**Replace is total (not a merge).** A named profile is a *complete* rule-state
replacement: per-rule `enabled = false` (or color overrides) written in
`config.toml` do **not** carry into a named profile — the user must re-state
them in the profile file. Example: if `fqdn` is disabled in `config.toml` and
the user activates a profile silent on `fqdn`, `fqdn` returns to its
`default_enabled` (on). This is documented behavior, not a bug.

Precedence chain (unchanged in shape, [[feedback-reload-precedence-snapshot]]):

- **Active profile** — `--profile` flag, else `config.general.profile`, else
  none (= `config.toml` itself is the active rule set).
- **Theme** — `--theme` flag, else `config.general.theme`, else the active
  profile's `theme` field, else startup background-color detection.

CLI snapshots and the bg-detect result are taken once at startup and reused on
every reload, exactly as today.

## 3. Built-in catalog changes

### 3.1 Promotion (append at indices 12–17 — ordering is load-bearing)

The six domain patterns move from `assets/profiles/*.toml` into
`rules::builtin_rules()` **byte-for-byte** (patterns unchanged — already audited
and tested). They are **appended after the existing 12 built-ins, at fixed
indices 12–17, in this exact order**, so that every existing priority-0
tie-break is preserved unchanged:

| Index | Rule | Priority | `default_enabled` | dark fg (inline, see §3.3) |
|-------|------|----------|-------------------|-----------------------------|
| 12 | `instance_id` | 100 | `true` | orange family |
| 13 | `region` | 100 | `false` | green |
| 14 | `arn` | 200 (envelope) | `true` | rose family |
| 15 | `container_id` | 100 | `false` | orange family |
| 16 | `image_tag` | 200 (envelope) | `false` | rose family |
| 17 | `pod_name` | 100 | `false` | orange family |

The existing 12 built-ins keep `priority = 0` and gain `default_enabled = true`.
`BUILTIN_NAMES` grows from 12 to 18 entries (promoted names appended at the
end). The overlap resolver's tie-break is `(Reverse(priority), rule_index ASC)`
(`pipeline.rs:143-144, 244-245`); appending at 12–17 guarantees the promoted
rules never reorder the existing rules' relative indices, so invariants like
`mac_yields_to_ipv6` (ipv6 index 6 < mac index 7) hold exactly. **The plan MUST
NOT insert the promoted rules among the existing 12.**

### 3.2 The `default_enabled` / enable mechanism (engine change, not data)

This is the flagship feature and requires a real change to the compile-time
merge — the current merge cannot re-enable an absent built-in (review B1/B2,
§13). Today `apply_user_rules_with_source` (`config.rs:511-541`) handles
`enabled = false` by `retain`-dropping the built-in (lossy: a dropped rule
cannot be re-added), and `enabled = true` on a built-in not present in the
working vec hits a silent `continue` (the code even comments that re-enable
"can't happen"). The new design:

1. Add `default_enabled: bool` to `BuiltinRule`. The 12 existing rules +
   `arn` + `instance_id` are `true`; `region`/`container_id`/`image_tag`/
   `pod_name` are `false`.
2. `load_builtins` seeds a **mutable working `enabled` state** for each of the
   18 rules from `default_enabled`. All 18 stay in the working set through the
   theme + profile/user merge.
3. `apply_user_rules_with_source` **mutates `enabled` in place** for an override
   naming a built-in (both `enabled = true` and `enabled = false`), replacing
   the `retain`-drop. So `enabled = true` on a default-off built-in finds it in
   the working set and flips it on; `enabled = false` flips it off.
4. A single **final `retain(|b| b.enabled)`** runs after all layers, right
   before regex compilation. Disabled built-ins are never compiled or matched.

For an existing config, the *final compiled rule set is identical* to today
(same active rules, same styles) — only the intermediate representation
changes. The per-line scan / feed loop (`pipeline.rs` hot path) is **unchanged**.
The `config.rs:529-541` comment asserting re-enable "can't happen" is rewritten.

### 3.3 `default_config_toml` / `tayf init` must respect default-off

`default_config_toml` (`config.rs:619-661`) iterates `builtin_rules()` and emits
each as a `[[rules]]` entry — today it never writes `enabled`. After promotion
it would write the four default-off rules as plain (enabled) entries, which —
per §3.2 — would turn them **on**, re-arming the FP landmines (review B2). The
generator MUST emit `enabled = false` for any built-in whose
`default_enabled == false`. Both consumers (`tayf init`, TUI `Shift+D`
init-from-dump) inherit the fix. A regression test asserts a freshly generated
`config.toml` leaves `container_id` off.

### 3.4 Theming the promoted rules (with anti-collision constraint)

Themes are `[[rules]]` lists overriding built-in colors by `name`
(`pattern`/`enabled` rejected). Each shipped theme gains entries for the six new
rules:

- `assets/themes/dark.toml` — dark Neon values (matching inline defaults).
- `assets/themes/light.toml` — light-adapted values for all six.
- `assets/themes/classic.toml` — named-ANSI / terminal-adaptive values.

**Anti-collision is a design constraint, not a data tweak** (review I3). The old
per-profile inline colors reused two hexes across rules (`#ff7a4d` for
instance_id/container_id/pod_name; `#ff6bb3` for arn/image_tag) — fine when only
one domain profile was active, but as always-available built-ins a user enabling
several gets indistinguishable colors, and always-on `arn`'s rose sits one nudge
from `uuid`'s magenta (`#ff5bf0`). Requirement:

- The two always-on additions (`arn`, `instance_id`) get hues distinct from each
  other **and** from the nearest existing 12 (esp. `uuid #ff5bf0`,
  `filename #ffac3b`).
- The orange-family trio and rose-family pair are differentiated enough that a
  user enabling 2–3 of them can tell them apart.

Exact hex values are tuned on a real terminal during implementation
([[feedback-tui-visual-needs-real-terminal]], [[feedback-no-ceremony-for-data-changes]]),
but the *distinctness* is mandated and asserted (the oracle reads colors live and
can assert `arn_fg != uuid_fg`, `instance_id_fg != filename_fg`, etc.).

`region` (default-off) keeps its 34-entry enum, which is a **dated snapshot**
(2026-05-26). Its rule doc-comment + README note that the enum is a snapshot
requiring patch releases for new regions, and a CHANGELOG line records it
(review I5). It stays default-off per the "catalog all six" decision.

## 4. Profile schema, loading, and active resolution

### 4.1 Schema simplification

The bespoke profile schema collapses into the config rule schema:

- **Before:** `Profile { rules: Option<Vec<String>>, append_rules: Vec<ProfileRule>, theme: Option<String> }`.
- **After:** `Profile { rules: Vec<UserRule>, theme: Option<String> }`.

A profile file is a strict subset of `config.toml`: a `[[rules]]` list (each
entry a `UserRule` — built-in override by name, or a new pattern, with
`enabled`/`style`/`styles`/`priority`) plus an optional top-level `theme`. The
`ProfileRule` type and the `rules`-whitelist concept are deleted; a profile that
wants only some built-ins disables the rest with `enabled = false`. A profile
rule named like a built-in is an **intentional override** (recolor / toggle),
not a collision error (this is the new "recolor built-ins" behavior, §1.2).

### 4.2 What survives of `validate_profile`; error routing

`validate_profile`'s old Phase-1 checks (unknown-builtin whitelist, built-in
collision) **dissolve** — the whitelist is gone and built-in-name-as-override is
now intended. What survives, applied to the profile's `UserRule`s: name-shape
predicate (`name_is_valid`) and duplicate-name-within-the-profile. New-rule
"must have a pattern" is enforced by the shared `apply_user_rules_with_source`
path (`config.rs:572-581`), which profile rules flow through.

**Error routing (resolves the rev1 §4.2↔§7.1 contradiction, review #4/#6):** keep
a dedicated rule source so a profile's rule/compile/styles errors report the
**profile file path**, not `<config>`. Rename `RuleSource::EmbeddedProfile` →
`RuleSource::DiskProfile` (it is no longer dead — disk profiles use it) and keep
its existing error-routing arms (`rules.rs` `compile_error_for` + the
styles/range collectors → `Error::Profile` / `Error::ProfileValidation` carrying
the path). Disk-profile rules therefore do **not** route through `UserConfig`.

### 4.3 Loading + active resolution (replace)

`profiles::load(name)` keeps disk discovery + **all** security guards —
`name_is_valid`, path canonicalization, symlink-out rejection, regular-file
check, `read_capped` (CLAUDE.md §3). The **embedded fallback is removed** (§7).

`lib.rs` and `reload.rs` resolve the active rule set before compiling:

1. effective profile name = `--profile` snapshot, else `config.general.profile`.
2. if a name is set → `profiles::load(name)` → active rules = profile's `rules`;
   else active rules = `config.rules`.
3. effective theme = `--theme` > `config.general.theme` > profile `theme` >
   bg-detect.
4. compile built-ins (substrate, with `default_enabled`) + active rules + theme.

`Compiled::load_with_theme` drops its `profile: Option<&Profile>` /
`profile_path` params; the caller passes the resolved active rule set. The
ownership-sound approach (review #5): build a synthetic owned
`Config { general: config.general.clone(), rules: active_rules }` (both `Config`
and `GeneralSection` are `Clone`) and pass it. **`compile_from_config`
(`rules.rs:918`, the TUI compile entry) also resolves a profile by name today and
MUST be updated to the same shared resolution** — the plan factors the
resolution into one helper used by `lib.rs`, `reload.rs`, and
`compile_from_config`. Call sites of the 6-arg signature (~13: `lib.rs:230/1160`,
`reload.rs:158`, `rules.rs` defs + `compile_from_config`, `profiles.rs` test
helpers, 5 `pipeline.rs` test sites, `benches/throughput.rs`) are updated in the
plan.

## 5. Enable/disable (toggle without deleting)

A first-class, non-destructive on/off for any rule (built-in or user), built on
the §3.2 engine change. The new surface is the TUI:

- **Toggle key:** `Space` on the Patterns tab (currently a no-op toast there —
  repurposed). Toggling **stages** an `enabled` flip for the selected rule:
  - toggle-OFF reuses the existing suppress-via-`enabled = false` synth-UserRule
    mechanism (the deletion/suppress path in `compile_pending.rs`);
  - toggle-ON of a default-off built-in stages a synth `UserRule { enabled =
    true }` (works because all 18 built-ins are in the merge set, §3.2).
  - `PendingEdits`/`RuleEdit` gains an `enabled`-flip representation (today it
    carries only `pattern` + `styles`).
  - `Ctrl+S` persists the flip to the active profile file (= `config.toml` in
    this sub-project, §6.3).
- **Visibility:** the Patterns list shows each rule's **effective** enabled state
  (computed from the merged/filtered state, not the raw catalog) — e.g. a dim
  row or `[x]`/`[ ]` marker — so default-off rules are discoverable by browsing.
  The **Detail pane shows it explicitly**: a `Status: enabled` / `Status:
  disabled` line, styled so the state is unmistakable (explicit user
  requirement, 2026-06-02).

Disabling preserves the rule's definition (pattern, color), so re-enabling
restores it. This is what makes `container_id` (and the other default-off
built-ins) usable.

## 6. TUI changes

### 6.1 Profiles tab rework

Rework the list-only embedded view into real profile management:

- **List** the default profile (`config.toml`) plus every disk profile under
  `~/.config/tayf/profiles/`.
- **`Space`** = set the selected profile active (writes `[general] profile`;
  selecting the default clears it).
- **Create** a new profile — **clone** the current active rule set into
  `profiles/<name>.toml` or start empty. Name prompt reuses the name-validation
  predicate + safe-write-destination guard.
- **Delete** a disk profile (confirm modal; the default cannot be deleted).
- The embedded-copy (`o`) handler is **removed** — no embedded library to copy.
- The render snapshot `tabs_profiles_init.snap` is regenerated (review #8).

### 6.2 Patterns tab + discoverability

- Add the `Space` enable/disable toggle (§5); default-off built-ins are listed
  (dimmed) and so discoverable.
- Detail pane gains the `Status:` line (§5).
- Existing edit actions (`c`/`e`/`o`/`r`/`d`/`n`) unchanged, targeting
  `config.toml`.
- **Discoverability beyond the TUI** (review I4): `tayf config dump` lists all 18
  built-ins with their effective enabled state (drops the embedded-profile
  section, §7); README + `--profile`/`--help` text enumerate the four default-off
  rules and the one-line enable recipe (`[[rules]] name = "container_id" enabled
  = true`).

### 6.3 Scope boundary (deferred — next sub-project)

Editing a **named** profile's rules *in the TUI* (color/regex/add/toggle
retargeted to that profile's file) requires retargeting the snapshot / save /
merge / reconcile machinery, hard-wired to `config.toml`. **Out of scope for C**
(accepted 2026-06-02). In C, all rule editing targets `config.toml` (the default
profile); a user customizes a named profile by editing its file directly. To
avoid the silent foot-gun (review N3), when a named profile is active the TUI
shows a visible note (e.g. status line: "active profile: <name> — edit its file
directly; edits here target the default profile"). The full in-TUI per-profile
editor is the next sub-project after C.

## 7. Removal of the embedded library + clean removal of retired names

### 7.1 Removal

- Delete `assets/profiles/{aws,docker,k8s,gcp,network}.toml` (their patterns now
  live in `builtin_rules()`; `gcp`/`network` were filter-only, replaced by
  per-rule `enabled = false`).
- Remove `EMBEDDED_PROFILES`, `embedded_profile_names`, `embedded_source`, and
  the embedded-discovery branch in `profiles::load`.
- Rename `RuleSource::EmbeddedProfile` → `RuleSource::DiskProfile` (§4.2); it
  stays live for disk profiles. Sweep now-dead embedded helpers:
  `profile_name_from_path_label`'s `<embedded:profile/` branch (`rules.rs:963`),
  the stale `profile_path: embedded only` comment in `compile_from_config`
  (`rules.rs:934`) ([[feedback-stale-dead-code-reason-drift]]).
- `tayf config dump` drops its embedded-profile section (`dump_cmd.rs`); update
  the dump test + `tabs_profiles_init.snap`.
- `App::Catalog.embedded_profile_names` and its TUI consumers are removed.

### 7.2 The `--profile` flag survives

`--profile` and `[general] profile` remain — they now select **disk** profiles
only. CLI help updates (drop "embedded"; describe disk profiles +
default-off-rule recipe).

### 7.3 Retired names → clean removal (no shim)

**Decision (2026-06-02):** tayf went public at v0.10.0 (2026-06-01); there are no
real users with persisted `profile = "aws"` configs yet. The project owner
explicitly authorized a clean removal, relaxing CLAUDE.md §4's one-minor
deprecation for this case. Therefore: **no soft-alias, no special migration
error messages.** Requesting a retired name (`aws`/`docker`/`k8s`/`gcp`/
`network`) with no matching disk file yields the standard `Error::Profile {
NotFound }` (which already lists the searched path). `CHANGELOG.md` documents the
removal and that the rules are now built-in (with the enable recipe for the four
default-off rules, and an explicit note that `aws`'s `region` is now opt-in).

## 9. Testing strategy

- **Colors via re-tone-proof oracle** ([[feedback-retone-proof-oracle]]): read
  promoted-rule colors live from `builtin_rules()` / theme compile; assert
  `== runtime` and `!= other`, never a hardcoded hex. Add anti-collision
  assertions (`arn_fg != uuid_fg`, `instance_id_fg != filename_fg`, the
  orange-family rules mutually `!=`).
- **Promoted patterns:** migrate positive-shape + negative-FP assertions from
  `profiles.rs`/`integration_profiles.rs` into `rules.rs` built-in tests
  (instance_id length/case; region enum + invented-region; arn envelope-wins +
  trailing-punctuation; pod_name base32 + git-hash rejection; image_tag two
  branches + FP guards; container_id 12-hex + git-hash collision now **gated
  behind enable**).
- **Prose-immunity (always-on):** pin `arn` negatives (`warn:aws`, `alarm:aws`,
  `modern:aws`) and `instance_id` negatives (`multi-<17hex>`, `wifi-<17hex>`,
  `i-<16hex>`, `i-<18hex>`, uppercase `i-<17HEX>`).
- **`default_enabled`:** with no config, `arn`/`instance_id` fire and
  `region`/`image_tag`/`container_id`/`pod_name` do **not**; with `[[rules]] name
  = "container_id" enabled = true`, container_id fires (the re-enable path —
  guards review B1); with `enabled = false` on a default-on built-in, it stops.
- **`default_config_toml`:** a freshly generated config keeps the four default-off
  rules off (`enabled = false` emitted) — guards review B2.
- **Priorities:** `arn`/`image_tag` priority 200, the other four 100, base 0 —
  asserted at their fixed built-in indices 12–17 (replacing the old
  `priorities[12+pos]` profile tests). Append-order invariant pinned (e.g.
  `mac_yields_to_ipv6` still holds).
- **arn envelope independent of region (review I2):** with default config (region
  OFF, arn ON), `arn:aws:ec2:us-west-2:111…:vpc/1.2.3.4` still suppresses interior
  `ipv4`/`uuid`. Drop/rewrite `aws_arn_wins_over_interior_region_pattern` (region
  no longer default-fires). Note: the old `http_status` interior-collision (audit
  C-14) is obsolete — that rule was removed pre-v0.12.
- **Profile load + replace:** a disk profile's `[[rules]]` replaces
  `config.toml`'s when active; built-ins remain substrate; total-replacement
  (config disables don't carry); theme precedence (config > profile.theme > bg);
  path-traversal/symlink/cap guards intact; profile rule errors report the
  **profile path** (DiskProfile routing).
- **Deprecation/removal:** retired name → standard `NotFound` (byte-pinned).
- **TUI:** Profiles-tab list/activate/create/delete state assertions
  (+ regenerated `tabs_profiles_init.snap`); Patterns `Space` toggle stages the
  flip (ON for default-off, OFF for default-on); Detail `Status:` line rendered
  (assert on buffer; color/state per [[feedback-tui-visual-needs-real-terminal]]);
  dump lists 18 built-ins with state.
- **Hot path unchanged:** `apply_rules`/feed behavior byte-identical for
  already-colored streams; guarded by the oracle + `security-review`.

## 10. Scope, ceremony, and out-of-scope

**In scope:** §3 (catalog + `default_enabled` engine + `default_config_toml` fix
+ themes/anti-collision), §4 (profile schema + DiskProfile routing + load +
replace + shared resolution), §5 (enable/disable engine + TUI), §6.1–6.2
(Profiles tab rework, Patterns toggle + Detail status + discoverability), §7
(removal + clean retirement), §8 docs.

**Out of scope / deferred (next sub-project):** in-TUI editing of a *named*
profile's rules (snapshot/save/merge/reconcile retarget) — §6.3.

**Estimated size:** ~900–1200 LOC (src + tests). Touches `rules.rs`,
`config.rs` (merge engine + `default_config_toml`), `profiles.rs`, `lib.rs`,
`reload.rs`, `assets/themes/*`, `src/config_tui/` (profiles tab, patterns tab,
events, app catalog, compile_pending, dump_cmd, snapshot), `cli.rs`, `error.rs`
(if DiskProfile routing needs it), `ARCHITECTURE.md`, `CHANGELOG.md`; deletes
`assets/profiles/*` and large blocks of embedded-profile tests; regenerates one
render snapshot.

**Important correction (review):** this is **not** "compile-time data only." The
compile-time merge in `apply_user_rules_with_source` changes (the
`default_enabled`-seeded enabled flag + final filter, replacing the lossy
`retain`-drop). The per-line scan / feed *hot path* is unchanged; behavior for
existing configs is identical.

**Ceremony (BIG but disciplined):** parallel spec review (done — §13) →
group-by-group subagent-driven TDD with per-task spec-compliance + code-quality
review → final Opus cross-cutting review over the whole C diff →
`security-review`. The catalog change + engine merge change + removal churn make
the cross-cutting + security gates non-optional ([[feedback-cross-cutting-review-value]]).
Theme color *values* are data (lean) — but anti-collision distinctness is a
mandated, tested constraint (§3.4). Regex promotions + engine changes keep full
TDD + the FP bar.

**Pre-commit gate (every commit):** `cargo fmt --check` + `cargo clippy
--all-targets -- -D warnings` + tests. The full `cargo test` hangs locally on

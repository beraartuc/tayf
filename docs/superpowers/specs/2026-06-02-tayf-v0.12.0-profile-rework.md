# tayf v0.12.0 — Profile rework (sub-project C)

**Status:** approved design (2026-06-02). Built on [[project-v0-12-0-shipped]]
(sub-project A) and [[project-v0-12-0-b-shipped]] (sub-project B), both on local
`main`, unpushed (HEAD `83dc72c`).

**Goal:** Make tayf "just work" for domain output (AWS / Docker / Kubernetes)
without making the user opt into a profile first, and re-cast the *profile*
feature from a fixed domain bundle into a **personal, switchable preset** of
which rules are active and what color each rule has.

---

## 1. Context & motivation

This is **sub-project C of the three-part v0.12.0 effort** (see
[[project-v0-12-0-shipped]]):

- **A — First-run & `init`** (shipped to local `main`).
- **B — TUI UX & polish** (shipped to local `main`).
- **C — Profile rework (this spec).**

A, B, and C land directly on `main` (no feature branches) and ship as a single
`v0.12.0` release: pushed together once C is done, with one `Cargo.toml` bump
(`0.11.0` → `0.12.0`) + tag at that joint push. This spec is written and
committed during development, then removed from `HEAD` before the joint push —
the same pattern A and B used. History keeps the design; `HEAD` stays clean.

### 1.1 The pivot (why this is not "composable profiles")

B's spec forward-pointed to C as "user-centric *composable* profiles" (opt-in
rule-packs). Brainstorming on 2026-06-02 rejected that framing. The decisive
observation: **nobody runs `tayf` and then opens the config to select the `aws`
profile before doing AWS work** — they just run their command. Opt-in friction
defeats the purpose of a colorizer. So the embedded domain profiles
(`aws`/`docker`/`k8s`/`gcp`/`network`) carry a "select me first" tax that almost
no one pays.

The fix is to **promote the FP-safe domain rules into the built-in catalog** so
they fire by default, and to **retire the embedded profile library** entirely.

The one hard constraint is the project's built-in pattern bar
([[feedback-builtin-pattern-bar]]): a built-in must be ~zero-false-positive,
shape-unique, and prose-immune, because it is on for *everyone*. Auditing the
six domain rules against that bar:

| Rule | FP risk | Default-enabled built-in? |
|------|---------|---------------------------|
| `arn` | very low — literal `arn:aws` prefix, prose-immune | yes |
| `instance_id` | low — `i-` + exactly 17 hex | yes |
| `pod_name` | low–medium — double-hash suffix, base32 (no vowels) | no (ships, opt-in) |
| `image_tag` | medium — has FP guards (host:port, JSON, module:line) | no (ships, opt-in) |
| `region` | low FP **but** 34-entry enum = maintenance if always-on | no (ships, opt-in) |
| `container_id` | **high** — 12-hex collides with git short hashes everywhere | no (ships, opt-in) |

So all six patterns are preserved (no domain value lost), but only the two
slam-dunks are on by default. The other four ship as **default-disabled
built-ins**, available to anyone via the new per-rule enable toggle. This
neatly defuses the `container_id` git-hash landmine *without* a rule-pack
mechanism, and it showcases the enable/disable feature.

### 1.2 What "profile" means now

A profile is no longer a domain bundle. A profile is a **named, switchable
preset = {which rules are active, and each rule's color/style}**, built on top
of the built-in substrate. `config.toml` *is* the default profile; named
profiles are alternative presets the user creates and switches between.

## 2. Core model

Three rules govern the model:

1. **`config.toml` is the DEFAULT profile.** Its `[general]` and `[[rules]]`
   are unchanged → zero migration for existing users.
2. **Named profiles** live at `~/.config/tayf/profiles/<name>.toml` and use the
   **same `[[rules]]` schema** as `config.toml`. They are selected with the
   `--profile <name>` flag or `[general] profile = "<name>"`.
3. **Replace semantics.** When a named profile is active, its `[[rules]]` are
   used *instead of* `config.toml`'s `[[rules]]`. Built-ins remain the
   **substrate** in every profile (a profile enables/disables and recolors them
   and adds user patterns on top). `[general]` (theme, banner, active-profile
   pointer, …) always comes from `config.toml`.

Precedence chain (unchanged in shape, [[feedback-reload-precedence-snapshot]]):

- **Active profile** — `--profile` flag, else `config.general.profile`, else
  none (= `config.toml` itself is the active rule set).
- **Theme** — `--theme` flag, else `config.general.theme`, else the active
  profile's `theme` field, else startup background-color detection.

CLI snapshots and the bg-detect result are taken once at startup and reused on
every reload, exactly as today.

## 3. Built-in catalog changes

### 3.1 Promotion

The six domain patterns move from `assets/profiles/*.toml` into
`rules::builtin_rules()` **byte-for-byte** (patterns unchanged — they are
already audited and tested). They keep their overlap priorities so existing
overlap-resolution behavior is preserved:

| Rule | Priority | `default_enabled` | dark fg (inline) |
|------|----------|-------------------|------------------|
| `arn` | 200 (envelope) | `true` | `#ff6bb3` |
| `instance_id` | 100 | `true` | `#ff7a4d` |
| `region` | 100 | `false` | `#36e08a` |
| `image_tag` | 200 (envelope) | `false` | `#ff6bb3` |
| `container_id` | 100 | `false` | `#ff7a4d` |
| `pod_name` | 100 | `false` | `#ff7a4d` |

The existing 12 built-ins keep `priority = 0` and gain `default_enabled = true`.
`BUILTIN_NAMES` grows from 12 to 18 entries. Overlap resolution (priority-DESC
sort, then first-match-wins) is **unchanged** — only the data it sorts grows.

### 3.2 The `default_enabled` mechanism

Add a `default_enabled: bool` field to `BuiltinRule`. The compile path
(`Compiled::load_with_theme`) computes each built-in's *effective* enabled state:

```
effective_enabled(builtin) =
    if an active rule (config or profile) overrides this name → that rule's `enabled`
    else builtin.default_enabled
```

A built-in whose effective state is `false` is dropped from the compiled rule
set (not compiled, never matched). This generalizes the existing behavior where
a user `[[rules]] enabled = false` disables a built-in (already supported — see
the `fqdn` disable test in `config.rs`); the only new capability is a built-in
that starts *off* and is turned *on* by `enabled = true`.

### 3.3 Theming the promoted rules

Themes are `[[rules]]` lists that override built-in colors by `name`
(`pattern`/`enabled` are rejected in themes). Adding six built-ins means each
shipped theme gains entries for them:

- `assets/themes/dark.toml` — the dark Neon values (matching the inline
  defaults in §3.1).
- `assets/themes/light.toml` — light-adapted values for all six.
- `assets/themes/classic.toml` — named-ANSI / terminal-adaptive values.

The inline `builtin_rules()` style is the dark default; theme files override per
background. Exact light/classic hex values are a **data choice** tuned on a real
terminal during implementation ([[feedback-no-ceremony-for-data-changes]],
[[feedback-tui-visual-needs-real-terminal]]) — not a logic decision. The four
default-disabled rules are themed too, so enabling one looks correct on every
background.

## 4. Profile schema, loading, and active resolution

### 4.1 Schema simplification

The bespoke profile schema collapses into the config rule schema:

- **Before:** `Profile { rules: Option<Vec<String>>, append_rules: Vec<ProfileRule>, theme: Option<String> }`
  with a separate `ProfileRule` type (mandatory `pattern`).
- **After:** `Profile { rules: Vec<UserRule>, theme: Option<String> }`.

A profile file is a strict subset of `config.toml`: a `[[rules]]` list (each
entry a `UserRule` — built-in override by name, or a new pattern, with
`enabled`/`style`/`styles`/`priority`) plus an optional top-level `theme`. The
`ProfileRule` type and the `rules`-whitelist concept are deleted; a profile that
wants only some built-ins simply disables the rest with `enabled = false`.

### 4.2 Loading

`profiles::load(name)` keeps its disk discovery and **all** security guards —
`name_is_valid` predicate, path canonicalization, symlink-out rejection,
regular-file check, `read_capped` (CLAUDE.md §3). The **embedded fallback is
removed** (§7). Parse + rule validation reuse the config rule-validation path so
a profile's rule errors are reported with the profile's file path. Failures
surface as `Error::Profile` (load/parse/path) or the rule-validation error
variant carrying the profile path.

### 4.3 Active resolution (replace)

`lib.rs` and `reload.rs` resolve the active rule set before compiling:

1. effective profile name = `--profile` snapshot, else `config.general.profile`.
2. if a name is set → `profiles::load(name)` → active rules = profile's `rules`;
   else active rules = `config.rules`.
3. effective theme = `--theme` > `config.general.theme` > profile `theme` >
   bg-detect.
4. compile built-ins (substrate, with `default_enabled`) + active rules + theme.

`Compiled::load_with_theme` drops its `profile: Option<&Profile>` /
`profile_path` parameters; the caller passes the resolved active rule set (e.g.
via an effective `Config` carrying `config.general` + the active rules). The
exact signature is finalized in the plan and flagged for parallel review.

## 5. Enable/disable (toggle without deleting)

A first-class, non-destructive on/off for any rule (built-in or user). The
engine already honors `UserRule.enabled`; §3.2 adds the default-off case. The
new surface is the TUI:

- **Toggle key:** `Space` on the Patterns tab (currently a no-op toast there —
  repurposed). Toggling stages an `enabled` flip for the selected rule; `Ctrl+S`
  persists it to the active profile file (= `config.toml` in this sub-project,
  see §6.3).
- **Visibility:** the Patterns list shows each rule's effective enabled state
  (e.g. a dim row or a `[x]`/`[ ]` marker), and the **Detail pane shows it
  explicitly** — a `Status: enabled` / `Status: disabled` line, styled so the
  state is unmistakable. (Explicit user requirement, 2026-06-02.)

Disabling preserves the rule's definition (pattern, color), so re-enabling
restores it. This is what makes `container_id` (and the other default-off
built-ins) usable: a Docker user flips it on once and keeps its color.

## 6. TUI changes

### 6.1 Profiles tab rework

Today the Profiles tab only lists embedded profiles (Space=activate, `o`=copy
embedded→disk). Rework it to manage real profiles:

- **List** the default profile (`config.toml`) plus every disk profile under
  `~/.config/tayf/profiles/`.
- **`Space`** = set the selected profile active (writes `[general] profile`;
  selecting the default clears it).
- **Create** a new profile — either **clone** the current active rule set into
  `profiles/<name>.toml` or start empty. Name prompt reuses the existing
  name-validation predicate and safe-write-destination guard.
- **Delete** a disk profile (confirm modal; the default profile cannot be
  deleted).
- The embedded-copy (`o`) handler is **removed** — there is no embedded library
  to copy from.

### 6.2 Patterns tab

- Add the `Space` enable/disable toggle (§5).
- Detail pane gains the `Status:` line (§5).
- Existing edit actions (`c` color, `e` regex, `o` override, `r` reset,
  `d` delete, `n` new) are unchanged and continue to target `config.toml`.

### 6.3 Scope boundary (deferred)

Editing a **named** profile's rules *in the TUI* (color/regex/add/toggle
retargeted to that profile's file) requires retargeting the snapshot / save /
merge / reconcile machinery, which is currently hard-wired to `config.toml`.
**This is out of scope for C** (accepted 2026-06-02). In C, all rule editing
targets `config.toml` (the default profile); a user customizes a named profile
by editing its file directly (same `[[rules]]` TOML they already know). The
full in-TUI per-profile editor is **the next sub-project after C**.

## 7. Removal of the embedded library + deprecation

### 7.1 Removal

- Delete `assets/profiles/{aws,docker,k8s,gcp,network}.toml` (their patterns now
  live in `builtin_rules()`; `gcp`/`network` were filter-only and are replaced
  by per-rule `enabled = false`).
- Remove `EMBEDDED_PROFILES`, `embedded_profile_names`, `embedded_source`, and
  the embedded-discovery branch in `profiles::load`.
- Remove `RuleSource::EmbeddedProfile` if it goes dead (CLAUDE.md §4 — no dead
  code). Disk-profile rules carry `RuleSource::UserConfig` semantics (they are
  user-authored TOML). This is a mechanical merge of match arms.
- `tayf config dump` drops its embedded-profile section.
- `App::Catalog.embedded_profile_names` and its TUI consumers are removed.

### 7.2 The `--profile` flag survives

`--profile` and `[general] profile` remain — they now select **disk** profiles
only. Requesting a name with no matching disk file yields `Error::Profile {
NotFound }` as today.

### 7.3 Migration messaging for retired names

The five retired names (`aws`, `docker`, `k8s`, `gcp`, `network`) get a
**helpful, specific** error when requested and not present on disk, instead of a
bare `NotFound`:

- `aws`/`docker`/`k8s`: "the '<name>' profile was retired in v0.12.0; its rules
  are now built-in — `arn` and `instance_id` are on by default; enable
  `region`/`image_tag`/`container_id`/`pod_name` with `enabled = true` in your
  config."
- `gcp`/`network`: "the '<name>' filter profile was retired in v0.12.0; disable
  built-ins you don't want with `[[rules]] name = \"…\" enabled = false`."

Error messages are user-facing UX (CLAUDE.md §4) and are byte-pinned in tests.
This is graceful guidance for an upgrading user, not a permanent alias.

## 8. Backward compatibility & migration

- Existing `config.toml` (`[general]` + `[[rules]]`) works unchanged — it is the
  default profile.
- Users who set `[general] profile = "aws"` (etc.) get the §7.3 migration error
  on first run after upgrade, pointing at the exact fix.
- Two new patterns (`arn`, `instance_id`) become visible by default. Both clear
  the FP bar (literal `arn:aws` prefix; `i-`+17-hex). No previously-uncolored
  prose should newly colorize beyond these shape-unique tokens — covered by FP
  regression tests (§9).
- CLI help for `--profile` updates (drop "embedded"; describe disk profiles).
- `ARCHITECTURE.md` profile/precedence sections update.
- `CHANGELOG.md` records: domain rules promoted to built-ins; embedded profile
  library retired; profiles re-cast as personal presets; per-rule enable/disable.

## 9. Testing strategy

- **Colors via re-tone-proof oracle** ([[feedback-retone-proof-oracle]]): read
  promoted-rule colors live from `builtin_rules()` / theme compile; assert
  `== runtime` and `!= some-other`, never a hardcoded hex.
- **Promoted patterns:** migrate the positive-shape and negative-FP assertions
  from `profiles.rs`/`integration_profiles.rs` into `rules.rs` built-in tests
  (instance_id length/case rejection; region enum + invented-region rejection;
  arn envelope-wins + trailing-punctuation; pod_name base32 + git-hash
  rejection; image_tag two branches + FP guards; container_id 12-hex + git-hash
  collision now gated behind enable).
- **`default_enabled`:** with no config, `arn`/`instance_id` fire and
  `region`/`image_tag`/`container_id`/`pod_name` do **not**; with
  `[[rules]] name = "container_id" enabled = true`, container_id fires; with
  `enabled = false` on a default-on built-in, it stops (regression-guard the
  existing `fqdn` behavior).
- **Priorities:** `arn`/`image_tag` priority 200, the other four 100, base 0 —
  asserted at their built-in indices (replacing the old `priorities[12+pos]`
  profile tests). Envelope-wins overlap cases preserved.
- **Profile load + replace:** a disk profile's `[[rules]]` replaces
  `config.toml`'s when active; built-ins remain substrate; theme precedence
  (config > profile.theme > bg) holds; path-traversal/symlink/cap guards intact.
- **Deprecation:** each retired name yields its specific migration message
  (byte-pinned, [[feedback-test-assertion-specificity]]).
- **TUI:** Profiles-tab list/activate/create/delete state assertions; Patterns
  `Space` toggle stages the flip; Detail pane renders the `Status:` line (assert
  on the buffer; color/state per [[feedback-tui-visual-needs-real-terminal]]).
- **Hot path unchanged:** `apply_rules`/feed loop behavior stays byte-identical
  for already-colored streams; guarded by the oracle + `security-review`.

## 10. Scope, ceremony, and out-of-scope

**In scope:** §3 (catalog + `default_enabled` + themes), §4 (profile schema +
load + replace), §5 (enable/disable engine + TUI), §6.1–6.2 (Profiles tab
rework, Patterns toggle + Detail status), §7 (removal + deprecation), §8 docs.

**Out of scope / deferred (next sub-project):** in-TUI editing of a *named*
profile's rules (snapshot/save/merge/reconcile retarget) — §6.3.

**Estimated size:** ~800–1100 LOC (src + tests). Touches `rules.rs`,
`config.rs`, `profiles.rs`, `lib.rs`, `reload.rs`, `assets/themes/*`,
`src/config_tui/` (profiles tab, patterns tab, events, app catalog, dump_cmd),
`cli.rs` (help), `ARCHITECTURE.md`, `CHANGELOG.md`; deletes `assets/profiles/*`
and large blocks of embedded-profile tests.

**Ceremony (BIG but disciplined):** parallel spec review (Rust senior + domain
senior) → group-by-group subagent-driven TDD with per-task spec-compliance +
code-quality review → final Opus cross-cutting review over the whole C diff →
`security-review`. The hot path is touched only as compile-time data, but the
catalog change + removal churn make the cross-cutting + security gates
non-optional ([[feedback-cross-cutting-review-value]]). Theme color *values* are
data and skip ceremony ([[feedback-no-ceremony-for-data-changes]]); the regex
promotions and engine changes keep full TDD + the FP bar.

**Pre-commit gate (every commit):** `cargo fmt --check` + `cargo clippy
--all-targets -- -D warnings` + tests. The full `cargo test` hangs locally on
the `e2e_overhead_smoke` PTY test — run `cargo test --lib` plus the relevant
`config_tui_*` / `integration_tui_*` / `integration_profiles*` targets instead.
No `unwrap`/`expect`/`panic` in library code.

## 11. Decision log (brainstorm 2026-06-02)

1. **Core model:** drop the rule-pack idea; promote FP-safe domain rules to
   built-ins; keep `--profile` as a *personal preset* mechanism, not a domain
   bundle.
2. **Promotion policy:** catalog all six; `arn` + `instance_id` default-on; the
   other four default-off built-ins (no separate FP audit; the bar is met by
   keeping borderline rules off by default).
3. **Profile ↔ config:** `config.toml` = default profile; named profiles are
   alternative rule sets that replace it when active; built-ins are the
   substrate.
4. **Enable/disable:** first-class, non-destructive; `Space` toggle on Patterns;
   explicit `Status:` line in Detail.
5. **TUI depth:** profile management (list/switch/create/delete) + enable/disable
   now; in-TUI editing of named profiles deferred to the next sub-project.
6. **Embedded library:** retired; `--profile` flag kept for disk profiles;
   retired names get helpful migration errors.

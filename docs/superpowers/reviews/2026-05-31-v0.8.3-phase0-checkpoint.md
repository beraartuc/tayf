## Decision: BOTH levers → ACCEPT-DOCUMENTED. Perf series declared DONE.

The dominant remaining cost in tayf's pipeline is the **irreducible regex scan**. v0.8.0–v0.8.2 already captured the structural wins (H1 line-buffer O(1), H2 single snapshot/line, H4 chunk-level feed). What is left — the `RegexSet::matches` + `find_iter`/`captures_iter` work — is paid on every byte regardless of any restructuring a no-match fast-lane or a sort/load micro-opt could do. Neither lever beats the measurement noise floor; both trend slightly negative. Per spec §8 and the explicit user instruction ("if apply_rules is near-optimal → ACCEPT-DOCUMENTED + finish perf, don't chase diminishing returns"), perf is done.

## H5 — no-match fast-lane → ACCEPT-DOCUMENTED (do not implement)

**What was spiked:** the exact shippable shape (boolean gate: `compiled.set.is_match(run)` → on `false`, `memrchr` last `\n`, write `run[..=last_nl]` verbatim, buffer the tail; on `true`, the unchanged per-line path). Byte-identity sanity (`feed_output_independent_of_chunk_boundaries` + all `pipeline` lib tests) PASSED on the spike — the shape is correct.

**`pipeline_feed` (in-process, criterion; the clean signal), base → spike:**

| shape | base MiB/s | spike MiB/s | Δ | criterion |
|---|---|---|---|---|
| prose | 138.10 | 125.31 | **−9.26%** | regressed |
| log | 25.536 | 24.444 | −4.28% | regressed |
| ansi | 108.01 | 105.35 | −2.46% | regressed |

**e2e (`tayf_ms`), base → spike:** prose 327.70→343.99, log 1001.38→1032.50, ansi 418.90→439.71 — all higher, BUT confounded: the pipeline-independent `bypass_ms` rose ~+20% in the same run (prose 150.27→182.05, log 145.63→176.00, ansi 167.75→201.55), i.e. ambient load, not the spike. e2e is therefore not clean evidence; the in-process micro-bench is.

**Verdict:** No prose win — prose stayed ~125–138 MiB/s, an order of magnitude below the hypothesized ~446 ceiling. **Mechanistic reason (noise-independent):** `RegexSet::is_match(whole_run)` visits every byte just like the sum of per-line `RegexSet::matches(line)`, so the regex work is a wash; the fast-lane only reclaims the small per-line bookkeeping (`load_full` + scratch clears) that v0.8.2's H2/H4 already made cheap, then adds its own guard + `memrchr` + redundant `feed_data_run(tail)` overhead on top → net neutral-to-negative. The v0.8.2 "446 MiB/s" hint came from a *different*, non-byte-identical L1 spike that skipped per-line framing entirely; it never predicted a boolean-gate fast-lane. Spike-first prevented shipping a complex byte-identical DOKUNULMAZ rewrite that yields no win.

**Disposition:** ACCEPT-DOCUMENTED. No `src/pipeline.rs` logic change. The premise is recorded as falsified so a future cycle does not re-propose it without a new mechanism.

## H6 — apply_rules internals → ACCEPT-DOCUMENTED (do not implement)

**What was probed:** combined ceiling of H6-a (skip final `runs.sort_by_key` when ≤1 contributing rule) + H6-b (skip priority `sort_by` when priorities uniform). H6-c (per-run `load_full` hoist) was not coded (too invasive for a throwaway; expected ~one atomic refcount/line — the smallest of the three; ACCEPT-DOCUMENTED by transitivity since the two cheaper opts already show no gain). 789 lib tests passed on the probe (the opts are byte-identical).

**`pipeline_feed/log` (the apply_rules-dominant shape), base → probe:**

| shape | base MiB/s | probe MiB/s | criterion change | verdict |
|---|---|---|---|---|
| log | 26.625 | 26.702 | time [−1.30% / **−0.29%** / +0.80%], p=0.60 | **No change detected** |

**`throughput` (bare `apply_rules`/`select_runs`), base → probe:** ipv4-heavy −0.65% (p=0.15, noise); mixed-syslog **+2.12% time (regressed)**; captures-heavy +1.14% (noise); profile-k8s +4.77%, profile-docker +6.98%, profile-gcp +5.69% (regressed). The H6-b uniform-priority `windows(2)` scan + the H6-a contributing-rule counter add a branch/loop over the matched-index slice whose savings (an O(k) sort on k≤handful) are below what the guards cost — so the probe is flat-to-slightly-slower.

**Verdict:** combined H6 ceiling on the log shape = **0% ± noise (p=0.60)**, well below the >5% ship threshold; on the dedicated `apply_rules` bench it is mildly negative. The non-regex overhead (both sorts + load) is below criterion's measurement floor (~0.3% on the log shape) — i.e. the regex engine dominates `select_runs` to the point the sorts/load are unmeasurable. **Disposition:** ACCEPT-DOCUMENTED. No `src/rules.rs`/`src/pipeline.rs` logic change.

## Consequences for v0.8.3 scope

- **Ships:** the EN-cleanup (Task 1, comment-only, commit `cefd49d`) — independent of the perf outcome, valuable regardless.
- **No perf code change.** `src/pipeline.rs` / `src/rules.rs` logic is byte-identical to v0.8.2; the only edits are comments (EN-cleanup). The spec §10 `security-review` gate was conditioned on a DOKUNULMAZ *logic* change → not triggered; a quick milestone `security-review` of the (comment+docs) diff is still run per CLAUDE.md §3 and will be trivially clean.
- **§7 closed.** tayf cannot meet the literal "<20% vs cat" target on bulk streams (a byte-transforming wrapper that scans every byte with regex cannot reach native `cat`); the honest disposition is the relative v0.8.x improvement (prose ~3.0×, log ~1.7×, ansi ~2.1× cumulative vs v0.8.0) plus this proof that the remainder is the regex floor.
- **Deliberate non-goal (documented, not silently closed):** the only remaining theoretical lever is a *matching-strategy* redesign — a single combined regex, an Aho-Corasick literal-prefix prefilter, or SIMD scanning — which is a major architectural change out of scope for a v0.8.x perf finale. If ever pursued it needs its own design cycle.

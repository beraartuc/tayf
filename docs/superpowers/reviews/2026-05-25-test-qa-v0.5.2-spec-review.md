## 🟡 Important (fold before implementation)

- **Spec §8.0 file-granularity enumeration is too loose for the high-risk surface (`spec:577-596`).** §8.0 lists test **files** but the "Specific high-risk surface" sub-list at 591-596 only names 5 tests. v0.5.2 extends `RuleSource` (new variant) and re-routes dispatch — every Theme-source dispatch test is now also implicit coverage for the EmbeddedProfile arm being symmetric. Per memory `feedback_enumerate_tests_for_invariant_claims`, the high-risk list must be exhaustive, not exemplary. Add: `validate_theme_rules_phase1_accepts_non_digit_styles_keys` (themes.rs:1122), `validate_theme_rules_collects_multiple_styles_key_errors_in_one_pass` (themes.rs:1089), tests 13/14/15 of `integration_capture_groups.rs` (lines 519-674), and `dispatch_*` tests at rules.rs:2435 / 2519 / 2538 / 2555. D7 needs to grep for ALL of these by name.

- **`ProfileRuleErrorKind::AppendRuleConflictsWithBuiltin` wording omits `styles.` prefix convention (`spec:430`).** Existing `ThemeRuleErrorKind` Display uses `styles."<key>": ...` (error.rs:117, 122, 129, 134, 146, 152, 174). The new profile variants use `append_rules entry "ipv4": ...` and `rules entry "ipv5": ...` — different quoting prefix. This is **acceptable** (different namespace: `styles.` is map key, `append_rules` is array element), but the spec §6.3 must explicitly document the divergence so D7 doesn't flag it as duplicate-formatter drift (memory `feedback_duplicate_formatter_audit`). One sentence under the table: "ProfileRule errors live in `[[append_rules]]` / `rules = [...]` namespaces — not `styles.` map keys — hence the `append_rules entry "X"` and `rules entry "X"` prefix instead of `styles."X"`."

- **Test 15 hot-reload timing assertions are best-effort, not byte-pinned (`plan:3140-3159`).** The cyan-present + timestamp-SGR-count-≤1 guards are sound in spirit but the comment "This is best-effort given PTY output interleaving" (plan:3151) is a flake invitation under macOS CI (memory `feedback_flaky_watch_test`). Two fixes before implementation: (1) increase post-edit `thread::sleep` from 800 ms to ≥1500 ms — `integration_hot_reload.rs:97` baseline is 300 ms for **settle**, reload takes additional notify-backend latency, so 800 ms is undersized; (2) add a deterministic synchronization marker (e.g., `echo TAYFMARK_POSTRELOAD` per `integration_hot_reload.rs:1-14` section-boundary pattern) so the test splits pre/post-reload output unambiguously instead of counting global SGR occurrences.

- **Test 9 `cli_profile_arg_parses_as_option_string` is under-specified (`spec:613-614`).** Spec describes `--profile foo --profile bar → clap error` but doesn't pin the error wording or exit code (clap typically emits exit 2, not 64). Add to §8.1 #9: expected exit code + a substring of the clap error message. Without this, the test ships as `assert!(out.status.code() != Some(0))` which is a no-op gate.

- **`ProfileRule` field shape: spec doesn't justify the absence of `enabled` (`spec:128-137`).** `UserRule` has `enabled: bool` (config.rs:87) but `ProfileRule` does not. Brief intuition: a disabled append rule is meaningless — but the spec should say so in a one-line doc-comment on the `ProfileRule` struct so future contributors don't add it "for symmetry". Suggest adding to §4.1 the line: "No `enabled` field — appending a disabled rule has no effect; users disable rules via the user-config `[[rules]] enabled = false` precedence path instead."

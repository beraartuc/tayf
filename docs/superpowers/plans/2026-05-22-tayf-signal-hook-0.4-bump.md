# signal-hook 0.3 → 0.4 Dependency Bump Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade `signal-hook` from `0.3.18` to the latest `0.4.x` (currently `0.4.4`, published 2026-04-04) without behavioral change. This is a pre-v0.2.1 staging move so that v0.2.1 hot-reload work begins on the current upstream baseline.

**Architecture:** No source-level refactor is expected. signal-hook 0.4.x's only published breaking change between 0.3 and 0.4 is in `low_level::pipe` (now takes `OwnedFd` instead of `IntoRawFd`). `tayf` does not use `low_level::pipe` — it uses only `signal_hook::consts` and `signal_hook::iterator` (`Signals`, `Handle`), whose public surface is unchanged across the 0.3 → 0.4 boundary. Therefore this plan is a **dependency bump** plus full verification chain, not an API port. The commit subject reflects that honestly.

**Tech Stack:** Cargo (`Cargo.toml`, `Cargo.lock`), signal-hook 0.4.4, cargo-audit 0.22, cargo-deny 0.19, existing CI workflow (`.github/workflows/ci.yml`).

**Non-goals (explicit):**
- SIGHUP wiring (deferred to v0.2.1 hot-reload spec).
- Any behavioral change to `src/signals.rs`.
- Any public-API change to the `tayf` crate.
- Version bump of `tayf` itself (this is an intermediate maintenance commit on `main`, not a release; no tag).

**Rollback:** A single `git revert <hash>` undoes the change cleanly (no migration scripts, no public-API impact).
